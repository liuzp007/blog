事情是这样的。

上周我在手机上打开自己写的那个 3D 页面，差点没把我吓一跳，风扇嗡嗡转，帧率掉到个位数，整个页面跟放幻灯片似的。我当时就愣住了，电脑上明明丝滑得不行啊。

坦率的讲，3D 页面好看是真好看，但贵也是真贵。GPU 这东西，桌面端和移动端的差距比你想象的大得多。我自己的感受是，如果你一开始没把性能当回事，等到上线那天再来优化，基本就是在还债。

所以我琢磨了一下，把这一套东西整理出来了，核心就三件事，移动端优先降级，帧内做最小的工作，后处理效果能省就省。

## 移动端降级与总开关

说真的，降级这事很多人都知道要做，但到底怎么判断该不该降，很多人没想清楚。我自己踩过坑，一开始写了个检测屏幕宽度的逻辑，结果平板横屏的时候也给我降级了，搞得页面丑得不行。

后来想明白了，降级的判断标准应该是多维的，不能光看一个条件。

```ts
export function useLite3D() {
  const mobile = /mobile/i.test(navigator.userAgent)
  const pref = localStorage.getItem('lite3d') === '1'
  const query = new URLSearchParams(location.search).get('lite') === '1'
  return mobile || pref || query
}
```

你看这个 Hook，三重判断叠在一起。第一个是 UA 检测，识别移动设备。第二个是用户本地偏好，有人就是想要省电模式，你尊重他就好。第三个是 URL 参数，这个我自己调试的时候特别好用，随时加个 lite=1 就能切换模式，不用改代码重新编译。

反正我觉得这种东西就该做成 Hook 复用，不要在每个组件里重复写判断逻辑。

## 帧内最小工作

这块是我觉得特别容易被忽略的地方。

很多人写 useFrame 的时候，上来就塞一堆计算，矩阵运算、物理模拟、粒子更新，全往里扔。然后跑起来发现帧率不稳，还不知道问题出在哪。

你想想看，useFrame 每一帧都会执行，60fps 的情况下一秒跑 60 次。你里面多做一个除法运算，看着没啥，但积少成多，帧时间就上去了。

```tsx
useFrame(({ clock }) => {
  mesh.current.rotation.y += 0.2 * clock.getDelta()
})
```

注意看这里用了 clock.getDelta()，不是写死一个增量值。这个细节挺重要的，因为 getDelta 给你的是上一帧到这一帧的真实时间差，这样不管帧率怎么波动，动画速度都是稳定的。

我有时候觉得，帧内代码就该像写嵌入式似的，每一行都得掂量掂量它值不值得在这一帧执行。不是所有东西都需要每帧更新，有些低频变化的完全可以隔几帧算一次。

## 后处理链路的取舍

说到这个后处理，我是真的觉得很多人对它又爱又恨。

爱的是效果确实好看，Bloom 一开，整个画面质感立马就不一样了。恨的是它吃性能吃得太狠了，尤其在移动端，简直是灾难级别。

```tsx
<EffectComposer>
  <Bloom intensity={0.6} />
  {/* <TiltShift2 enabled={!lite} /> */}
  {/* 更多效果按需启用 */}
</EffectComposer>
```

你看我这边的做法，Bloom 保留了一个低强度的，因为它是性价比最高的后处理效果，一点点就能让画面亮起来。但像 TiltShift2 这种，直接注释掉了，不是不好看，而是它的性能开销和带来的视觉提升不成正比。

我跟你说，后处理这块的核心思路就是克制。别一上来就把 EffectComposer 里塞满，Bloom 加一个就够了。你可以先在桌面端把效果调好，然后到移动端一个个关掉试试，你会发现关掉一半的效果之后，画面其实没那么大差别，但帧率直接稳了。

其实吧，做 3D 页面跟做菜挺像的，食材再好，调料放多了也会毁掉整道菜。先守住帧率，再慢慢往上加效果，这个顺序不能反。

你的页面在用户手机上是卡还是顺，可能就差在几个后处理 Pass 上。要不要试试把你项目里的后处理精简一下，看看效果？
