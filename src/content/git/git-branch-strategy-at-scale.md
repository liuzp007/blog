事情是这样的。

我之前待过一个团队，十几号人，业务跑得挺快。当时大家没什么分支策略的意识，就是各拉各的分支，做完了往 main 上合。刚开始还行，人少嘛，冲突也不多，PR 随便看两眼就过了。后来业务线多了，新人也进来了，有次发版前合并，十几个分支怼在一起，冲突文件几十个，光解决冲突就搞了两天。最后勉强发出去，线上还是炸了。

那次事故之后，领导拍板说，咱们得搞规范，上 GitFlow。于是大家老老实实搞了 develop 分支，搞了 release 分支，搞了 hotfix 流程。规范文档写了十几页，贴在 Confluence 上，全员宣导。

坦率的讲，刚开始确实好了不少。至少发布不再是一锅粥了，该走的流程都在走。

但大概过了三个月，新的问题来了。release 分支上的补丁攒了一堆，回流到 develop 时各种冲突，develop 和 main 的差异越拉越大。有个同事离职了，他手上的分支没人敢动，因为没人知道那个分支的代码到底能不能合。到了发版那天，大家又开始加班到凌晨，只不过这次不是在解决 main 上的冲突，而是在解决 develop 和 release 之间的冲突。

我当时就寻思，这不是从一个坑跳进另一个坑了吗。

后来我自己复盘了很多次，慢慢想通了一件事。分支策略这玩意，你把它当规范来搞，基本上注定会走形。因为它不是在消灭问题，它是在搬问题。你把发布时的冲突搬到了回流时，把分支上的混乱搬到了规范文档的缝隙里。

我自己的感受是，分支策略更像是一个成本函数。

它不会让成本消失，只会让成本在不同的时间点、不同的人身上出现。你选了一套策略，就是在选把哪笔账先付、哪笔账后付、哪笔账转给别人。而你要做的，不是找一套所谓正确的策略，而是搞清楚你愿意为什么成本买单。

## 先把成本项列出来

说真的，很多人讨论分支策略的时候，连自己到底在为什么头疼都没搞清楚。冲突多？发布慢？线上炸了找不到人？这些问题背后的成本其实就那么几类。

评审成本。你的 PR 有多大，变更是不是可读的，评审的人够不够用，评审速度快不快。

集成成本。分支之间冲突有多频繁，依赖有没有漂移，测试稳不稳定，跨团队的改动怎么对齐。

发布成本。发版有没有窗口期，需不需要变更冻结，灰度和回滚做得怎么样，测试环境和生产环境一不一致。

沟通成本。谁在做啥，线上跑的是啥，哪个分支能用，哪个分支能发。这些信息在团队里流转得好不好。

组织成本。权限怎么分，合规怎么做，责任边界在哪，跨时区怎么搞，人员流动了怎么交接。

很多团队踩的坑不是选错了策略，而是根本没想清楚自己最痛的是哪个成本项。他们看到冲突多，就搞个长期 release 分支来隔离，冲突确实少了，但环境一致性成本上来了，追责成本上来了，回滚成本也上来了。等于你用一份便宜的账单换了三份贵的，只不过那三份贵的不会立刻出现在你面前。

这就是成本函数被写错了。

## 几种策略的真实代价

坦率的讲，我不打算给你列一个分支策略对比表，那种东西网上到处都是。我想做的是把几种常见策略的真实账本翻开，让你看看每条路上你到底要付什么钱。

先说 trunk-based。

这玩法的核心就一句话，主干永远能集成、能测试、能发布。你拉短分支，高频合并，冲突在每天的开发里就暴露出来了。然后通过 feature flag 和灰度发布，把代码合并和功能上线拆开。

好处很明显。主干代表的就是真实状态，出问题了定位路径短。冲突更小更可控，因为变更很早就被合进去了。发布节奏可以独立于功能节奏，不用再等一堆功能凑一起发。

但代价也真实存在。它对工程纪律要求很高，测试、回滚、feature flag 这些必须是系统能力，不是某个项目组临时搞个脚本就行的。它对评审流程也有要求，PR 太大或者评审太慢，主干节奏直接就拖垮了。还有一个很容易被忽略的点，产品和管理层必须接受代码合并不等于功能交付这个事实，不然他们会逼着团队搞长分支来做隔离。

再说 GitFlow。

GitFlow 把环境的语义写进了分支名里，develop 负责集成，master 负责发布，feature/release/hotfix 各有各的角色。好处是发布准备这个动作变得很显性，什么时候进 release，什么时候合 master，流程清清楚楚。

但它引入了两个中心的复杂度。

团队规模一大，develop 和 release 之间的回流就成了常态，冲突在回流的地方集中爆发。依赖升级、基础设施改动这类横跨多个模块的变更，会在两个中心之间来回拉扯。还有那个经典矛盾，hotfix 必须从 master 分出来，但修复的代码可能得基于最新的 develop 才能跑，于是团队开始形成各种隐性规则，最后没人能说清楚当前的代码到底是什么状态。

我自己的感受是，GitFlow 适合那些发布窗口严格、每次发布需要稳定候选集的场景。如果你的组织确实存在集成节奏和发布节奏必须分离的情况，它不是不能用。但你要清楚自己在为两个中心的维护成本买单。

最后说很多人实际在用的，主干加 release 分支。

主干继续开发，release 分支冻结候选集，只有修复能进。这种策略的关键不在于你有没有 release 分支，而在于两个问题。release 分支活多久。上面的修复怎么回流。

如果 release 分支长期存在，它就会变成第二根主干。如果只活一两周，那它更像一次发布的快照。长期存在的 release 分支会产生一种东西，我叫它回流利息。你越晚回流，冲突越大。你越频繁回流，流程越复杂。你不是在减少风险，你是在把风险从发布当天挪到回流时刻，并且把回流成本变成了一个长期税。

## 怎么做决策

聊了这么多代价，你可能想问，那我到底该选哪个。

说真的，我不觉得这是一道选对选错的题。我更愿意把它拆成三个层次，每个层次对应一类成本。你不用一次选完美，但你需要能持续迭代你的成本函数。

第一层，你的主干能不能发布。

这个问题的答案会决定你走哪条大方向。如果能，那你在走 trunk-based 的路，你需要投资自动化测试、发布机制、feature flag、评审效率这些东西。如果不能，你得回答另一个问题，谁承诺可发布。是 release 分支吗，是某个环境分支吗，还是根本没人承诺。承诺不清的结果就是大家都以为别人会兜底，最后没人兜底。

第二层，发布节奏和开发节奏是不是绑死了。

如果你只能在某个时间窗口把一坨东西发布出去，那 release 分支或者 GitFlow 就是被自然推动的。如果发布是持续的、可拆分的、功能可以独立灰度，那 trunk-based 就更适合。

这里最容易犯的错是把我们一直这么干的当成只能这么干。有些约束只是组织习惯，你可以通过自动化和风险控制逐步松绑。但如果真的是硬约束，比如法规要求，那你就得接受它，然后围绕它优化。

第三层，并行开发的隔离需求到底来自哪里。

风险隔离的话，feature flag 通常比长期分支更合适。权限隔离的话，仓库边界、CODEOWNERS、发布管线的控制比每个团队一条分支更靠谱。只有交付隔离，就是多个版本并行维护那种，才真的需要长期分支。但这时候你要把它当作多产品线维护来管理，而不是把它当成正常开发流程的一部分。

## 两个能落地的工作流

光聊原理不落地也挺没劲的。下面给你两个工作流，它们的目标不是更优雅，而是把成本放在你能控制的位置，并且给事故留出恢复的路径。

### 工作流 A，主干可发布加短分支加 feature flag

适合持续交付、测试比较稳、愿意在发布能力上投资的团队。

核心原则就三条。分支生命周期短，小时到几天。PR 尽量小，评审尽量快。合并即集成但不等于交付，交付通过 flag 和配置控制。

```bash
# 从主干拉短分支
git checkout main
git pull
git checkout -b feat/search-ranking

# 保持短周期同步，降低冲突半径
git fetch origin
git rebase origin/main

# 合并时避免"功能未完成"污染主干：用 flag 把入口关上
git push -u origin feat/search-ranking
```

合并之后的发布策略是这样的。flag 默认关闭，上线只带代码不带功能。灰度打开 flag，观察指标和回滚路径是不是有效。完全打开之后删掉 flag，删除本身也要当作一次变更走评审。

这里有个很关键的认知。主干可发布不是指主干上没有未完成代码，而是指未完成代码不产生用户可见的影响，并且出了问题可以回滚。

### 工作流 B，主干开发加短周期 release 分支加严格回流

适合发布窗口固定、需要明确候选集，但不想搞完整 GitFlow 的团队。

核心原则也是三条。release 分支只为一次发布服务，生命周期短。release 上的修复必须回流到主干，回流有固定节奏。release 分支上的例外合入必须有明确的追责和复盘。

```bash
# 发布前从主干切 release（例如每周一）
git checkout main
git pull
git checkout -b release/2026-03-24
git push -u origin release/2026-03-24

# 只允许修复进入 release
git checkout -b fix/login-null-pointer
git commit -m "fix(auth): guard null pointer in login flow"
git push -u origin fix/login-null-pointer

# 合并到 release 后，必须回流到主干（可以用 cherry-pick 或 merge）
git checkout main
git pull
git cherry-pick <commit_sha>
git push origin main
```

这套流程的关键成本在回流纪律四个字上。如果你允许 release 分支积累大量修复但不回流，或者回流时机不稳定，你就会把冲突成本推迟并放大，最终把 release 分支变成第二主干。那就又回到老路上了。

## 几个高频反模式

聊完正事，再聊几个我在不同团队里反复见到的反模式。这些东西往往是团队为了短期止痛做出来的应激反应，短期确实能舒服一点，长期来看代价很大。

长期不合并的功能分支。

看起来隔离了风险，其实是在积累利息。主干上的接口、约束、测试策略每天都在变，分支活着越久越不兼容。合并的时候冲突不是多，是没有局部语义可依赖，整个代码你都不确定哪部分能直接用哪部分得重写。PR 变成巨型 diff，评审只能挑明显问题，系统性风险根本识别不出来。

当你觉得某个功能太大不能频繁合并的时候，通常你需要做的不是搞一条更长的分支，而是把需求拆小或者引入 flag。

用分支代替环境和发布控制。

test 分支、staging 分支、prod 分支，很多团队这么干。问题是环境本身是动态的，你把环境状态写进 Git 历史，然后分支指针来回移动，你根本没法回答线上跑的到底是哪一组提交。发布过程变成了一个把分支 merge 过去的仪式，而不是可审计的发布动作。环境差异被分支差异掩盖，最后排障全靠经验。

怎么说呢，更健康的做法是环境由部署系统来描述，Git 分支只描述代码演进，不要把两件事混在一个抽象里。

禁止 rebase 来保留历史。

有些团队为了追责，禁止 rebase，强制 merge commit。结果历史里充满噪声，反而更难追责。追责不是看有没有 rebase，而是看能不能从历史里读出意图和决策链，能不能准确定位引入变更的最小单元，能不能在事故时找到明确的恢复路径。

用禁止 rebase 来解决追责问题，大概率是在用流程替代工程能力。

把分支策略搞成信仰。

我们团队必须 trunk-based，我们团队必须 GitFlow，这种口号会把策略选择变成身份认同。一旦变成身份认同，任何问题都会被归咎于你没按我这套做，而不是回到成本函数本身去看哪里出了问题。策略要能演进，前提是它被当作一套可计算的成本分配，而不是信仰。

## 你得能量化才能迭代

如果你想让分支策略变成可迭代的系统而不是一次性拍板，你需要指标。指标不必复杂，但必须能把成本项显性化。

我建议至少跟踪这些。

PR 从创建到合并的中位数耗时，这个反映评审成本和吞吐量。PR 平均 diff 大小和超大 PR 比例，这个反映可读性和风险。合并冲突次数和平均解决耗时，这个反映集成成本。发布频率、发布失败率、回滚频率，这个反映发布成本和稳定性。热修复从发现到上线的耗时，这个反映事故恢复能力。

你会发现很多所谓的分支策略问题，追到底都是这些指标的异常。PR 太大，评审太慢，测试不稳，发布不可回滚。分支策略只能缓解症状，真正要治的是系统能力。

## 最后说说我的判断

我自己的判断很简单，但执行起来不轻松。

默认往 trunk-based 的方向走。它把问题暴露得更早、更小、更可控。前提是你愿意投资测试、发布和开关能力，不然它会把痛苦暴露得更快。

只有发布节奏存在硬约束的时候才引入 release 分支。而且要把 release 分支做成短周期快照，严格回流，避免第二主干。

不要用分支承担环境和交付控制。环境用部署系统描述，交付用开关和发布策略描述，Git 分支只承担协作和演进。

把策略变成成本函数的迭代，而不是一次性拍板。用指标观察，用复盘修正，把我们要不要换策略变成我们要把哪个成本项往哪挪，以及为什么。

当你的分支策略让团队在高并发协作里仍能快速评审、快速集成、快速发布，并且在事故发生时能最小化恢复路径，它就是对的。

反过来，如果你的策略只能靠更严格的规则来维持稳定，那稳定往往只是表象。你欠下的那些成本，早晚会在某个你不希望的时刻，以一种更难看的方式出现在你面前。

到时候再想改，可比现在难得多了。
