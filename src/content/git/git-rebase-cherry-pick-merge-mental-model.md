我之前待过一个团队，有个同事特别执着于 rebase，逢人就讲"线性历史才是王道"，搞得大家本地分支三天两头 force push，review 链接隔三差五失效，reviewer 打开 PR 一看 commit SHA 对不上，直接懵了。另一拨人则坚持 merge everything，结果主线历史长得跟藤蔓似的，git log 翻出去三页都找不到一个有意义的提交信息。

坦率的讲，两边都有自己的道理，但两边也都踩了坑。争论的根源其实不是 rebase 好还是 merge 好，而是大家没对齐一个东西，我们在用 Git 历史表达什么？历史到底在为谁服务？

我后来慢慢琢磨出一个自己觉得还挺好用的框架，这三种操作各自对应一种"语义承诺"。

merge 承诺的是保留并行演进的事实，让历史忠实反映协作过程。rebase 承诺的是把一组变化重放到新的基线上，优先线性叙事和审阅体验。cherry-pick 承诺的是抽取一段语义变化然后搬运走，优先局部迁移和救火效率。

承诺不同，风险就不同。你没法只要好处不要代价，这事没有白嫖的。

## 从 DAG 到叙事，Git 历史的本质不是线

说真的，很多人一上来就把 Git 历史当成一条直线来理解，这个直觉是有问题的。

Git 的对象模型是 DAG，提交指向父提交，可能有多个父，分支说到底就是个指针。你看到的所谓"线性历史"，只是你选择用某种方式展示 DAG 的结果，不是 DAG 本来长那样。

理解这一点还挺重要的。rebase 不是在"改变事实"，它是在重新编码事实的表达方式。merge 也不是"更真实"，它只是选择保留并行节点的显式结构而已。

当你把历史当作协作界面来看的时候，你要问自己的问题是，这个界面要表达"并行发生过"这件事，还是要表达"最终形成的因果链"？两者都合理，但适用的场景不一样。

## Merge，保真与可追溯，但审阅成本可能炸

顺着上面的再聊聊 merge。

merge 的核心价值就是保留并行。它让你在历史里能清楚看到两个分支曾经并行存在过，然后用一个 merge commit 表达"它们在这个点汇合了"。

我自己的感受是，merge 在下面这几种场景里特别有价值。

需要追溯协作过程的时候，比如什么时候分叉的、什么时候汇合的、冲突在哪解决的，merge commit 一目了然。需要明确边界的时候，一个 feature 分支的整个生命周期在 merge commit 上体现得非常清晰。还有需要稳定回滚的场景，如果你的团队用 merge commit 作为发布边界，那回滚就可以围绕边界做，干净利落。

但是 merge 的代价也很现实。如果你把分支上的 WIP 提交、噪音提交、修修补补的提交原样带入主线，主线会迅速变得不可读。很多人口口声声说"merge 保真"，但如果保留下来的全是噪音，那也只是把成本转移给了 reviewer 和未来的维护者而已。

不是哥们，那不叫保真，那叫甩锅。

## Rebase，审阅友好叙事清晰，但会改写身份

说到 rebase 这块，很多朋友可能觉得这就是个"整理提交"的工具，没那么复杂。但其实它的底层机制值得搞清楚。

rebase 的本质是重放。它把你的一串提交在新的基线上重新生成一串新的提交。新的提交有新的 SHA，旧的 SHA 不再是同一个对象。这带来两个很重要的后果。

一个是身份改写。任何引用旧提交 SHA 的东西，review 链接、故障定位记录、聊天里的引用，都会失效或者语义漂移。另一个是时间线重编码。提交时间和父子关系都变了，git blame 的指向可能更符合"最终叙事"了，但也可能更模糊了"真实发生过的过程"。

所以我对 rebase 的使用边界一直很明确。

在没被别人依赖、没发布的分支上 rebase，完全可以，成本可控。在已经被共享的分支上强行 rebase，通常不值得，除非你明确愿意承担同步成本，并且团队有成熟的流程来兜底。

有个比较常见也比较健康的模式是，个人分支随便 rebase，往主线合的时候用一种明确的策略，比如 squash 或者 rebase merge，但主线本身尽量少做历史改写。

这个边界搞清楚了，能少踩很多坑。

## Cherry-pick，救火的快刀，但会制造平行宇宙

怎么形容 cherry-pick 呢，它很像把某个提交当作一个补丁，整个搬运到另一个分支上去。

优势就一个字，快。

线上 hotfix 的时候，主线还在往前推，但你需要把一个修复搬到 release 分支上，cherry-pick 简直就是为此而生的。多版本维护的场景，同时维护 v2 和 v3，修复要同步到多个分支，cherry-pick 也很好使。还有回滚之后要再引入的场景，某个功能被回滚了，但里面有个子修复还是需要的，cherry-pick 直接摘出来。

但代价也很扎心，就是"平行宇宙"。

同一个语义变化会在不同分支上有不同的提交对象，不同的 SHA。以后你想合并这些分支的时候，Git 没法自动识别"它们其实做了同一件事"，冲突会更频繁，历史也更难解释。

所以 cherry-pick 的边界我一直觉得应该是，把它当救火工具，别当日常同步方式。如果你发现团队日常靠 cherry-pick 同步功能，大概率说明分支策略或者发布策略有结构性的问题，该修的是那个，而不是继续 cherry-pick。

## 选择标准，你在优化哪一种成本

回到一个更根本的问题，到底该选哪个？

我觉得这事的关键不是"哪种更高级"，而是"我们当前最痛的成本是什么"。

merge 优化的是协作过程可追溯性，代价是审阅噪音和历史复杂度。rebase 优化的是审阅和叙事的清晰度，代价是身份改写和共享分支的同步成本。cherry-pick 优化的是局部迁移速度，代价是平行宇宙和后续合并的复杂度。

在一个高频发布、强审阅、强回滚要求的团队里，你可能更希望主线历史清晰，并为回滚设计好边界。在一个需要强保真审计的环境里，你可能更强调 merge 的过程可追溯性。

没有标准答案，但有一个好的思考框架，就是先搞清楚你当前最不能接受的成本是什么。

## 实战，在同一个团队里组合三者

现实里很少有什么"全 rebase"或者"全 merge"的团队。更合理的做法是定义好组合策略。

个人分支上，允许 rebase，甚至鼓励，把 WIP 整理成可审阅的序列。主线合并的时候，用 merge commit 或者 squash merge，取决于你要不要保留并行事实。发布分支上，谨慎 cherry-pick 修复，但要记清楚"从哪摘来的"。

下面是一个典型流程示例，开发分支上重放并整理，合并到主线用 merge commit 保留边界

```bash
# 1) 在 feature 分支上整理提交（仅限未发布/未被他人依赖的分支）
git fetch origin
git rebase -i origin/main

# 2) 合并到 main，用 merge commit 保留"这是一次集成点"
git checkout main
git merge --no-ff feature/xxx -m "merge: feature xxx"
```

如果你希望主线更线性，又希望保留分支结构，可以考虑 rebase 的 `--rebase-merges`，但要清楚它更复杂，也更容易踩坑

```bash
git fetch origin
git rebase --rebase-merges origin/main
```

这块需要注意一下，`--rebase-merges` 不是万灵药，用之前最好在自己的分支上先试一遍，别直接在共享分支上搞。

## 冲突处理，你把冲突放到哪里，就把成本放到哪里

很多人有个误解，觉得"rebase 冲突更多"。

更准确的说法是，rebase 把冲突分摊到每个提交的重放过程中，merge 把冲突集中到一次合并点上。两者的总冲突量取决于变化的交错程度，跟操作叫什么名字没关系。

分摊和集中对应着不同的风险。

分摊的情况下，你可能在某个提交上解决了冲突，但语义上这个冲突应该在另一个提交里解决。历史的因果链就被污染了。集中的情况下，一次冲突解决可能混入了多种语义变化，回滚和 blame 都会更难。

我的经验是，如果你能保证提交序列本身是"可验证的叙事"，分摊冲突反而是有利的，因为它让每一步都保持了一致性。但如果你的提交本来就是 WIP，分摊只是把混乱拉得更长而已。

想想就觉得挺讽刺的，工具本身没有好坏，全看你喂进去的是什么。

## 几个非常典型的反模式

坦率的讲，下面这些场景我全都见过，有的甚至是我自己踩过的坑。

共享分支上强制 rebase，然后跟所有人说"自己处理一下"。结果是同步成本爆炸，review 链接全失效，团队信任直接下降。这玩意真的不是一句"你们 rebase 一下"就能解决的。

把 merge 当垃圾桶，什么乱七八糟的提交都往主线倒。结果是主线不可读，任何 blame 都像在抽奖，你查一个问题能翻出去五页 log 还没找到线索。

大量 cherry-pick 来回同步 feature。结果平行宇宙越来越大，最终合并的时候冲突成倍增长，解决一次冲突能让你怀疑人生。

还有为了追求所谓"线性"，把真实发生过的并行事实全部抹掉。历史看起来确实漂亮了，但复盘和追责的时候丢信息，出了问题谁也说不清当时到底发生了什么。

这些反模式背后有个共同点，就是把历史当作个人偏好，而不是团队协作界面。

## range-diff，重写历史后怎么证明语义没变

当你 rebase 或者做了大规模历史整理之后，最怕的就是"看起来一样，但其实变了"。

`git range-diff` 是一个我觉得特别实用但很多人不知道的工具。它比较两段提交序列的差异，是以提交为单位的，不是文件级别的 diff。你能看到哪些提交被改了、顺序怎么变了、内容怎么变了。

示例

```bash
# 比较 rebase 前后两段提交序列
git range-diff origin/main...HEAD@{1} origin/main...HEAD
```

你不需要把它当日常命令，但在"历史整形"这种高风险操作之后，它是我觉得最值得跑一遍的验证手段。鬼使神差地 rebase 了一堆东西之后，跑一下 range-diff 看看有没有歪掉，比啥都踏实。

## 我的判断，别争统一操作，要统一历史语义

说实话我也不确定我这套框架是不是最完美的，但它确实帮我在好几个项目里减少了很多无意义的争论。

我不建议团队规定"必须 rebase"或者"必须 merge"。我建议统一的是"历史语义"，主线历史希望表达什么？合并点需不需要边界？事故时回滚依赖哪种结构？reviewer 希望看到怎样的叙事？

当语义统一之后，操作会自然收敛为少数几种组合策略。

反过来，强推某个操作只会把成本转移给最倒霉的那个人。通常是 reviewer，是维护者，是值班工程师，以及半年后的你自己。

你想想看，半年后的你打开 git log，看到一堆乱七八糟的历史，那种无力感，是不是比现在多花十分钟对齐一下语义要难受得多？
