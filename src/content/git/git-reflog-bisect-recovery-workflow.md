事情是这样的。

去年有一次线上事故，我从下午两点搞到晚上九点，中间经历了好几个阶段，先是用 reset 回滚，然后发现回错了位置，接着又强推了一把，结果整个团队的状态全乱了，最后还是拉了组里最熟悉 Git 的同事帮忙才收拾了残局。事后复盘的时候我才发现，真正让我损失七个小时的，不是那个 bug 本身，而是我在慌乱中把所有能救我的线索都给抹掉了。

那次事故之后我就开始认真研究一件事，出了问题以后，Git 到底能怎么帮你从一团乱麻里把确定性找回来。

坦率的讲，在此之前我对 Git 的事故处理认知基本停留在「赶紧回滚」这个层面。但真正经历了一次之后我发现，事故发生的时候你最先失去的其实不是时间，而是确定性。你不知道问题从哪里冒出来的，不确定现在代码到底处于什么状态，更不敢确定回滚会不会搞出更大的事。很多团队把事故处理理解成赶紧改代码，但真正决定止损速度的，是你能不能在五分钟之内回答两个问题。第一，现在代码处于什么状态，它是怎么到这里的。第二，我们能以最小风险回到哪个状态，以及这个状态为什么安全。

说真的，我对 Git 在事故中的定位一直有个很明确的看法。它不是存代码的地方，它是你在不确定性里重建事实的工具链。Reflog 用来找回你以为丢了的提交，Bisect 用来把怀疑很多地方变成一个可验证的嫌疑点。这两样东西共同服务一个目标，最小恢复路径。

这篇文章我不打算给你罗列命令选项，那些文档里都有。我只聊一套流程，从事故现场到恢复点的路径该怎么设计，以及怎么避免把事故处理变成第二次事故。

## 事故现场的第一原则，先止血，再取证，再修复

很多事故之所以会升级，真不是因为技术不够，而是顺序搞错了。

正确的顺序是这样的。第一步是止血，先恢复服务到一个可接受的状态，这个状态不一定是最优的，但要稳定，可回滚，可解释。第二步是取证，把当前 commit、构建号、配置快照、日志、回滚动作全都记录下来。取证不是为了甩锅，是为了防止下次踩同样的坑。第三步才是修复，在隔离环境里定位根因，做最小改动，验证后再推上去。

Git 在这三个阶段都能帮上忙，但它的典型误用是什么你知道吗，就是团队一上来就在 main 上搞 reset 加强推，回滚完了又前滚，把历史和证据全给抹了。这样你就失去了复盘能力，也失去了下一次事故的止损能力。

我自己的感受是，把事故处理当作一套可复用的流程而不是临场发挥，是团队成熟度的一个分水岭。

## Reflog 到底记了什么

很多人把 reflog 当成一个神奇的回收站，以为它记了所有提交。其实更准确地说，reflog 记录的是引用在你的本地是怎么移动的，比如 HEAD、分支指针、stash 指针这些。提交对象本身存在于对象数据库里，只要没被垃圾回收清理掉，理论上就能找回。reflog 给你的是一条路径，告诉你该从哪里找。

这带出来三个很关键的东西。

第一，reflog 主要是本地证据。远端是否保留、保留多久、谁能看到，取决于服务端的实现和策略，你不能假设远端一定能救你。

第二，reflog 的核心价值在于把误操作可逆。reset、rebase、checkout、merge、pull，这些会移动引用的操作，都能在 reflog 里留下轨迹。

第三，reflog 不是无限期保险。它会过期，会被 GC 影响。事故处理要把找回变成及时动作，而不是事后祈祷。

我一直觉得吧，你应该把 reflog 看成飞机的黑匣子。它不保证你永远能还原一切，但它能在关键窗口期给你足够的事实。

## 最小恢复路径，把回滚拆成可验证的三个动作

我把自己总结的最小恢复路径定义成三个动作的组合，每个动作都要可验证。

第一个动作是定位安全基线。明确一个 commit 或 tag，作为已知可用的状态。第二个动作是回到安全基线。用最小风险的方式把生产带回这个状态。第三个动作是固化恢复点。让团队和系统都知道我们回到了哪里，并且必要时能继续前进。

这里的关键就两个字，可验证。一个没有验证过的回滚，坦率的讲，只是心理安慰。

在 Git 层面，最常见的安全基线来源有这么几个。上一次成功发布对应的 tag，这是最推荐的。主分支上某个已知稳定的 merge commit，这是次推荐的。CI 产物的版本号对应的 commit，如果你有强绑定的话也行。

有了安全基线之后，回滚方式取决于你的发布模型。纯 Git 层面通常是两条路。一条是 git revert，保留历史，新增一个反向提交，适合主线协作和审计。另一条是 git reset --hard 加强推，改写历史，风险大，只适合非常明确且受控的场景，比如临时分支或者误推到错误分支且还没被其他人依赖。

事故处理中，默认应该偏向 revert。因为它把风险显式化了，你不会在回滚过程中把证据给抹掉。

## 用 Reflog 找回丢失的提交

最常见的事故其实不是线上 bug，而是误操作把正确的东西弄丢了。比如 git reset --hard 回错了提交，比如 rebase 做坏了冲突解决后语义被污染了，比如强推覆盖了远端分支所有人都拉到了错误状态，再比如误删分支以为提交没了。

当你意识到我把东西弄丢了的时候，先别急着做更多操作。第一步是把现场保存成一个新分支，避免你继续移动 HEAD 导致证据被覆盖。

```bash
# 1) 先把当前状态固定下来，避免继续操作污染现场
git status
git branch rescue/incident-20260324
```

然后看 reflog。最常用的入口是 HEAD 的 reflog。

```bash
# 查看 HEAD 的移动历史
git reflog --date=iso

# 常见用法：只看最近 30 条
git reflog -n 30
```

你会看到类似 HEAD@{5} 这样的条目。核心不是记住格式，而是找到那次误操作之前的位置。找到之后你有两种策略。一种是创建一个新分支指向那个位置，最安全。另一种是直接 reset 回去，更激进。

我推荐先分支再决定怎么处理。

```bash
# 假设你要找回的点是 HEAD@{12}
git branch recovered/head-before-mistake HEAD@{12}

# 然后你可以 checkout 过去检查
git checkout recovered/head-before-mistake
```

如果你要恢复的是某个分支指针的移动，也可以看对应分支的 reflog。

```bash
git reflog show main -n 30
git reflog show feature/xxx -n 30
```

这块需要注意一下，关键思路是不要急着把主线改回去，先把正确的对象找回来并固定住。只要你把它固定成分支或 tag，它就不会轻易被 GC 清理，你就重新拥有了确定性。

## Bisect 的价值，把猜变成可重复的定位过程

很多团队定位 bug 的方式是什么呢，翻 diff，翻群聊，然后猜。在简单项目里凑合能用，但在多人协作和高频发布的环境下，这会变成一个时间黑洞。你会不断做无效尝试，每次尝试都在消耗团队的注意力。

Bisect 的核心价值是分治。你给它一个坏的点和一个好的点，它用二分法逼近第一个引入问题的提交。它把定位从我觉得是这个变成我能证明是这个。

但有个前提你得知道，bisect 要求可判定。你必须能对任意中间状态给出一个可重复的判断，好或者坏。这个判断可以是自动化测试，可以是编译是否通过，可以是某个关键接口是否返回正确值，也可以是关键页面能不能正常渲染。

一个典型的流程是这样的。

```bash
# 1) 找到一个确定坏的点（通常是当前 HEAD）
git bisect start
git bisect bad

# 2) 指定一个确定好的点（例如上一次稳定发布的 tag）
git bisect good v1.2.3

# 3) Git 会自动 checkout 到中间点，你在该点判断好/坏
# 判断后标记：
git bisect good
# 或
git bisect bad

# 4) 重复直到定位到第一个坏提交
git bisect reset
```

说真的，真正的难点在第三步。你怎么判断好和坏，既可重复又足够便宜？如果每次判断都要半小时，那二分法也救不了你。

## 把 Bisect 变成工程能力

成熟团队会把 bisect 的判定写成脚本。这样定位过程可以被复用、被并行、被复盘。git bisect run 可以让你把判定逻辑变成一个命令，返回 0 表示 good，返回非 0 表示 bad。

举个例子，用单元测试作为判定。

```bash
git bisect start
git bisect bad
git bisect good v1.2.3

# 用脚本自动跑判定：0=good, 1=bad
git bisect run bash -lc 'pnpm test --filter critical && pnpm build'
```

这类脚本的价值不在于更自动化，而在于更可解释。当你得到一个坏提交的时候，你知道它是在哪个判定规则下被判坏的。这对复盘和修复策略选择非常重要。

我自己的建议是，事故结束之后把这类脚本收敛成回归测试的最小集合。下一次同类事故你就能更快复用判定逻辑，而不是重新发明。

## Reflog 加 Bisect 的组合拳

顺着上面的再聊聊，这两个工具的关系是这样的。

Reflog 用于恢复确定性，找回正确的提交和状态，避免你在错误的地基上定位。Bisect 用于缩小不确定性，在好与坏之间找出第一个引入问题的变化。

一个很常见的场景是这样的。你本来在做 rebase 或者修复什么东西，结果把历史弄乱了，紧接着线上又出了问题。这时候你如果直接 bisect，很可能是在一个被污染的历史上二分，最后定位到一个看起来相关但其实只是 rebase 冲突解决造成的副作用的提交。

正确的做法通常是这样的。先用 reflog 找回未污染的基线，比如 rebase 前的 HEAD，或者发布 tag 对应的 commit。然后在该基线上标记 good 和 bad，再 bisect。

这样你定位到的才是真实引入问题的语义变化，而不是你在事故中制造的噪音。

## 常见的坑

下面这些反模式我见过太多次了，它们的共同结果是事故处理变成更大的事故。

第一个，在主分支上直接 reset --hard 加强推做回滚。结果证据被抹掉，其他人本地状态失配，后续修复和复盘成本暴涨。

第二个，没有固定现场分支就开始一顿操作。结果 reflog 条目被新的移动淹没，你丢掉了最关键的恢复线索。

第三个，把 bisect 当成最后手段，前面先猜三小时。结果浪费注意力窗口，错过最有效的止损时间。

第四个，bisect 判定不稳定，受网络、缓存、外部依赖影响，导致结果不可复现。结果定位到的提交无法证明，团队进入再次猜的循环。

第五个，把回滚等同于恢复，忽略配置、数据、缓存的版本兼容。结果代码回滚了系统仍然坏，大家以为 Git 不可靠，其实是恢复路径不完整。

事故里你最需要的是确定性。而强推、频繁改写历史、缺少证据固定，全都是在主动制造不确定性。

## 把恢复路径产品化

reflog 和 bisect 都不是什么高手命令。它们只是把事故处理从临场发挥变成可复用流程的两个抓手。

怎么说呢，我一直觉得你不应该把它们当作个人技巧，而要把它们产品化到团队流程里。发布必须产出可引用的安全基线，tag 或者可追溯版本号。每次事故结束都要沉淀最小判定脚本，让下一次 bisect 更快。主线回滚默认用可审计的方式，也就是 revert，除非有非常明确的例外条件和授权流程。任何高风险操作之前先固定现场分支，把确定性先留住。

当你把这些当作团队接口而不是个人偏好的时候，事故处理的速度和质量会发生质变。你会更少依赖英雄主义，更多依赖流程的可重复。

而这，恰恰是在不确定性里保持稳定产出的关键。
