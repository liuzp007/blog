去年有个朋友找我喝咖啡，说他们团队搞了三个月微前端，用的是 Module Federation。一开始挺兴奋的，把 react 和 antd 都配成了 shared，几个子应用也拆出去了，CI 跑得飞快。结果上线两周，线上开始出现偶发白屏，用户反馈渲染错乱，他们排查了整整一周才发现是远程加载了两个不同版本的 React，hook 规则全炸了。

他说了一句话我印象特别深，「早知道这么坑，我还不如不分。」

坦率的讲，这种故事我听得太多了。Module Federation（下面我简称 MF）这几年在微前端圈子里被聊得非常多，但也是最容易被误解的一项能力。很多人把它理解成「让多个应用共享依赖」「像 npm 一样加载远程模块」，于是落地路径也被带偏了，先把 shared 开起来，再把页面拆出去，再试图用 MF 替代发布流程。最后的结局通常是得到一个比单体更难维护的系统，线上偶发白屏、依赖版本冲突难以定位、回滚窗口被压缩、调试复杂度指数级上升。

说真的，我更愿意用一句话把 MF 的价值钉住。

**Module Federation 的核心是「跨构建边界的运行时装配与版本协商」，而不是「共享依赖」。**

共享依赖只是手段之一，而且是最容易引入系统性风险的手段之一。这篇文章我会从工程视角把 MF 的关键问题拆开聊聊，包括 MF 的运行时到底在干什么，为什么微前端的难点不是怎么拆而是怎么发布和治理，怎么设计边界才合理，以及我踩过的那些坑。

先聊聊微前端这件事到底在解决什么问题。

我有时候觉得，微前端这个词本身就有误导性。听到「微前端」三个字，很多人的第一反应是技术拆分，怎么把一个应用切成好几块。但实际上，当你去问那些真正落地了微前端的团队，他们最初的动力几乎从来不是「我想把代码拆开」，而是「我们的团队协作出了问题」。

团队规模变大之后，单体仓库的 CI 变慢了，发布要排队，代码评审变成了拉锯战。业务域之间的差异越来越明显，A 团队想两周发一次，B 团队想一天发三次，互相卡着。还有那种历史包袱和技术栈并存的情况，老系统不敢动，新系统又想用新技术栈，需要渐进迁移而不是一次重写。

这些问题的核心是组织与发布系统的问题，不是技术拆分问题。MF 能做的，是在某些边界上减少耦合成本，但它同时会引入新的耦合，运行时装配、版本协商、跨仓库兼容、灰度一致性，这些东西都会变成你要持续治理的债。

所以我一直建议把 MF 当成「组织结构的技术映射」，而不是「把页面切成远程模块的技术炫技」。你团队的组织边界在哪里，MF 的边界就应该在哪里。

那 MF 的运行时到底在做什么呢。

这块我尽量聊得直观一点。MF 产物里最关键的不是远程模块本身，而是一个叫 remote container 的东西，翻译过来就是远程容器。你可以把它理解成一个运行时可加载的模块注册表，里面有两个核心方法，一个叫 get，传入模块名就能拿到对应 exposed 模块的工厂函数。另一个叫 init，用来初始化共享作用域，告诉远程容器宿主这边提供了哪些共享模块以及它们的版本信息。

宿主侧的 runtime 做的事情其实就三步。第一步，加载 remoteEntry，就是那个容器脚本文件。第二步，初始化 share scope，把宿主这边提供的共享依赖版本信息注册进去。第三步，从远程容器 get 你要的目标模块，执行工厂函数，拿到 exports。

你可以把 MF 理解成「把模块图的一部分延迟到运行时才装配」。收益是什么呢，独立构建和发布的远程模块可以被宿主动态加载。代价呢，运行时的不确定性显著增加了。构建期能确定的东西，现在要等到用户打开页面那一刻才知道对不对。

说到共享依赖这块，我是真的觉得大部分人对它的理解太乐观了。

共享依赖听起来确实很美。多个子应用不用重复打包 react、antd 这些库，体积更小，加载更快，完美。但这句话背后藏着一个巨大的前提，共享依赖必须在版本、语义、实例层面保持一致，否则你会得到非常难排查的问题。

React 多实例，hook 规则报错、context 不共享、渲染行为异常。UI 组件库版本不一致，样式错乱、主题 token 不一致、运行时莫名其妙报错。状态库多实例，store 分裂、订阅失效、数据不同步。这些都不是理论上可能发生，是实际上一定会发生的事。

怎么说呢，共享依赖这件事，其实就是你把「依赖一致性」从构建期搬到了运行时。以前版本对不对，看 lockfile 就知道了，现在得看用户浏览器里实际加载了什么。而运行时一致性远比构建期一致性难治理，因为它涉及宿主与远程的版本组合矩阵，灰度发布时不同用户拿到的不同组合，CDN 缓存与回滚窗口，还有线上诊断与追溯，你到底加载了哪个版本，得查半天。

所以共享依赖不是默认选项，而是需要被严格治理的能力。

回到实际操作层面，先看一个最小配置。

```js
// host webpack.config.js（示意）
const { ModuleFederationPlugin } = require('webpack').container

module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'host',
      remotes: {
        // remoteName@url
        marketing: 'marketing@https://cdn.example.com/marketing/remoteEntry.js'
      },
      shared: {
        react: { singleton: true, requiredVersion: '^18.2.0' },
        'react-dom': { singleton: true, requiredVersion: '^18.2.0' }
      }
    })
  ]
}
```

```js
// remote webpack.config.js（示意）
const { ModuleFederationPlugin } = require('webpack').container

module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'marketing',
      filename: 'remoteEntry.js',
      exposes: {
        './Landing': './src/pages/Landing'
      },
      shared: {
        react: { singleton: true, requiredVersion: '^18.2.0' },
        'react-dom': { singleton: true, requiredVersion: '^18.2.0' }
      }
    })
  ]
}
```

这个配置看着简单，但里面至少有三点你必须搞清楚。

singleton 这个东西不是什么优化选项，它是正确性约束，至少对 React 这类依赖是这样。如果你不设 singleton，两个 React 实例同时存在，hooks 直接就废了。

requiredVersion 也不是装饰，它决定了版本协商的边界和失败策略。宿主说我要 ^18.2.0，远程带了个 17 过来，会怎样，这个你得心里有数。

还有 remoteEntry 的 URL，这东西是发布系统的契约。你怎么保证它可用、一致、可回滚，才是整个系统成败的关键。

说到发布模型，这块真的要好好聊聊。

我自己的感受是，MF 最大的工程风险就来自「运行时加载远程」这件事。一旦你开始运行时加载，发布模型的问题就立刻浮出水面了，宿主版本、远程版本、CDN 缓存、灰度策略，这些怎么组合。

给你说一个常见的事故路径。宿主发布了新版本，指向新的 remoteEntry 或者新 exposed 模块名。但远程还没发布，或者发布了但 CDN 还没同步完。用户拿到了宿主的新版本，去加载远程，失败了。白屏，功能缺失。

你会发现这和传统的 chunk load error 很像，但更难搞，因为 remote 是另一个团队、另一个仓库、另一个发布节奏。

所以我对 MF 发布模型的建议是把它当成一个「版本化装配系统」，至少要满足几个条件。

remoteEntry 必须版本化，用 buildId 或者 contenthash 目录都行。宿主与远程要有兼容窗口，旧的 remoteEntry 要保留足够长时间，覆盖回滚场景和长尾用户。灰度必须按「组合」来做灰度，宿主版本和远程版本的组合要么一致，要么可控。

一种更可控的方式是让宿主不直接写死 remoteEntry URL，而是通过一个远程清单来解析，把这份清单当成可灰度、可回滚的配置资产。

```js
// 伪代码：host 运行时根据 manifest 决定 remoteEntry
async function loadRemote(remoteName) {
  const manifest = await fetch('/mf-manifest.json').then(r => r.json())
  const url = manifest.remotes[remoteName]
  await loadScript(url) // 加载 remoteEntry.js
  // 之后 init share scope + container.get(...)
}
```

这不是唯一实现方式，但它体现了一个工程方向，把「远程地址」当成发布配置，而不是构建常量。

再聊聊边界设计。

微前端落地中最常见的错误我觉得就是按页面拆。把每个页面都变成 remote exposed module，觉得拆得越细越灵活。这样做会让系统边界变得极度细碎，宿主成了一个复杂的装配器，远程成了大量小模块的集合。远程数量一多，加载链路就长，失败概率就高。共享依赖的协商也更复杂了，版本组合矩阵直接爆炸。远程之间缺少明确的领域边界，演进也变得困难。

我更推荐的策略是把联邦化对象设计为「能力边界」。比如一个业务域的完整子应用壳或路由分支，一个可独立演进的复杂能力比如编辑器、可视化搭建器、支付流程，或者一个具有明确 API 和契约的组件集，但前提是你的版本治理已经比较成熟了。

这样你能把 MF 的风险控制在少数关键边界上，而不是把整个站点变成动态拼装。

故障域这块也得认真对待。

当你引入 MF 的那一刻，你必须接受一个事实，远程加载失败不是极端情况，而是系统必然会发生的事件。网络抖动、CDN 缓存、发布不同步、版本不兼容，任何一个都可能触发。所以你必须在架构上回答几个问题。

远程失败的时候，页面还能不能工作。是功能降级还是整页不可用。用户能不能得到明确的反馈。你能不能在监控和日志里追溯加载了哪个 remoteEntry、用了哪个共享版本。

工程上最基本的要求是把远程加载包装成显式的错误边界，对关键路径提供 fallback。

```js
// 伪代码：远程加载加错误边界与降级
async function safeImportRemote(moduleKey) {
  try {
    return await import(moduleKey) // 实际是 container.get(...) 的封装
  } catch (e) {
    // 记录 remoteName/url/版本信息，便于追溯
    reportFederationError(e)
    return { default: FallbackComponent }
  }
}
```

你不需要每个页面都写一遍，但你必须在平台层提供这类能力。不然远程失败就会以「偶发白屏」的形态出现，而且几乎无法在团队间协作定位。想想就头大。

聊了这么多，我也总结了几个最常见的反模式，给大家避避坑。

第一个，把 shared 开成「全共享」。把所有 node_modules 都 shared，版本协商直接变成噩梦。很多库根本不适合共享，它们可能依赖运行时全局，可能版本跨度大，可能有多实例副作用。共享越多，不确定性越大。共享应该是白名单，而且优先只共享正确性强约束的依赖，比如 react。

第二个，忽视 singleton 的正确性约束。React、路由、状态管理这类库通常要求单例语义，多实例会导致极难理解的行为差异。没有明确 singleton 策略的 MF 系统，通常会在规模变大后崩溃。

第三个，宿主与远程发布节奏无兼容约束。「各自独立发布」如果没有兼容窗口与契约测试，只会把集成测试从 CI 搬到线上。你需要对 exposed 模块的 API 做版本化，至少保证宿主新版本能在一段时间内兼容远程旧版本，或者反过来也行。

第四个，把页面拆成大量 remote modules 导致装配链路过长。装配链路越长，失败概率越高，调试成本越大。MF 更适合少数「重能力」的装配，而不是把整个 UI 切成碎片。

第五个，没有可观测性与追溯。MF 的问题往往是组合问题，宿主版本 X 加远程版本 Y 加共享版本 Z 加 CDN 缓存状态。没有统一的日志字段和错误上报，你几乎不可能复现。把 remoteEntry url、share 版本选择、加载耗时纳入日志，这是最低要求。

说到底，我对 Module Federation 的总体判断是偏克制的。它确实非常强大，但它把「集成成本」从构建期搬到了运行时。只有当你的组织和平台能力足以治理这种成本时，它才会带来净收益。

我会在满足几个条件时考虑用 MF。团队之间有清晰的领域边界和发布责任，远程不是谁都能改的公共区。有发布模型保障一致性，版本化目录、兼容窗口、灰度按组合推进、可回滚。有可观测性，能追溯远程地址、共享版本选择、加载失败原因与影响面。联邦化对象是能力边界，而不是页面碎片。

反过来，如果你只是想减少重复打包体积，MF 大概率不是最优解。更简单的做法通常是改善代码分割、依赖分层和缓存策略，成本更低，确定性更高。

MF 真正的价值不在共享依赖，而在让跨团队、跨仓库、跨发布节奏的系统仍然能在运行时被装配起来。要用好它，你需要把它当成架构系统来设计，而不是当成构建优化开关。

你准备好吃这个苦了吗。
