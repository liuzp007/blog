上周有个朋友在群里问我，说他们团队做了代码分割，按路由分包、按组件分包、把 vendor 也抽出来了，构建产物里一下子多了几十个文件，觉得自己优化得挺好。结果上线之后 chunk load error 的报错量反而翻了一倍，回滚的时候还发现旧版本的 chunk 已经被 CDN 清掉了。

我当时就跟他讲，你这不是在优化，你是在给自己挖坑。

代码分割这个事情，坦率的讲，是前端工程里最容易被口号化的能力之一。大家都在喊按需加载，都在喊把包拆小，你也能很快把配置写出来，构建产物里也能很快看到更多的文件。但这并不等于你获得了更快的用户体验，也不等于你获得了更稳的发布系统。

我想把话说得更直接一点，代码分割不是越碎越好，甚至碎本身不是目标。目标是什么？是控制成本函数。

这个成本函数至少包含四类成本。

网络成本，下载体积、请求数、并发队头阻塞、CDN 命中率。CPU 成本，解析、编译、执行，还有初始化时序。缓存成本，命中率、失效半径、hash 级联、版本不一致导致的加载失败。还有稳定性成本，部署过程的一致性，灰度和回滚的可行性，错误定位与追溯的成本。

说真的，如果你的团队只盯着第一类成本，就是首屏下载多少 KB 这件事，你很可能会做出对稳定性最不友好的切分。chunk 数量爆炸，hash 易级联，上线时更容易出 chunk load error，回滚变得困难。这篇文章要做的，就是把这些成本放到同一张桌子上，让你能用系统视角去做取舍。

## 把 chunk 当成发布与缓存单元，而不是文件切片

很多人把 chunk 理解为文件，把代码分割理解为把文件切小。这会导致一种特别常见的错误，就是把 chunk 的数量当作优化方向，把更细当作成功信号。

我自己的感受是，更准确的理解应该是，chunk 是一个发布单元与缓存单元。它背后对应的是一组模块的集合，就是模块图的一个分区，以及由运行时加载和装配的边界。它的价值不是更小，而是让必须同时出现的模块在同一个 chunk 里，减少额外请求和时序复杂度。让变化频率不同的模块分离开，减少缓存失效半径。让共享程度高的模块可以复用，减少重复下载和重复解析。让故障域可控，某个 chunk 失败不会拖垮全站，或者至少可诊断可回滚。

这也是为什么我一直在强调发布与缓存单元这个说法。你不是在切文件，你是在设计系统的变更传播路径。这块真的很重要。

## 分割的根，模块图分区加运行时装配

Webpack 里的代码分割，其实是对模块图做划分然后生成 chunk 图。你最终看到的文件，是这种划分的结果。你需要记住一个非常关键的事实。

分割的收益来自边界的意义，分割的代价来自边界的数量。

边界的意义通常来自两类差异。一类是生命周期差异，哪些模块只在某些路由或功能被用到，哪些必须首屏就有。另一类是变更频率差异，哪些模块几乎不变，比如框架和基础库，哪些天天变，比如业务代码和活动页。

边界的数量会引入这些代价。更多的请求与调度，哪怕 HTTP/2 也不是无限免费。更多的 runtime bookkeeping，chunk 映射、加载队列、错误处理。更复杂的部署一致性问题，HTML 和 manifest 与 chunk 版本错配更常见。更难的诊断与回归，哪个 chunk 变大了，谁引入了重复，谁导致了 hash 级联。

所以你不能用分割等于收益这种线性模型来做决策。你需要在边界意义和边界数量之间找到一个稳定的平衡点。

## 缓存策略的核心，控制失效半径与 hash 级联

缓存策略里最重要的不是你用了 contenthash，而是你能否控制一次变更会让哪些资源失效。这个 distinction 太关键了。

在 Webpack 场景中，hash 级联的常见触发器包括这么几个。模块或 chunk id 不稳定导致的重排。runtime 被嵌入到多个 entry 中导致的重复与联动变化。vendor 与业务混在一起导致的业务一改 vendor 也变。还有 splitChunks 规则不稳定，比如按体积阈值边界频繁跳变。

一个更可控的基础配置通常长这样，重点是意图而不是具体值。

```js
// webpack.config.js 片段：让 hash 级联可控，降低缓存失效率
module.exports = {
  output: {
    filename: 'js/[name].[contenthash:8].js',
    chunkFilename: 'js/[name].[contenthash:8].js',
    // publicPath 必须与部署策略一致（CDN/灰度/多环境）
    publicPath: '/assets/'
  },
  optimization: {
    // 把运行时抽出来，避免每个 entry 都携带一份 runtime
    runtimeChunk: 'single',
    // 尽量稳定 id，减少"模块位置变了 -> id 全重排 -> hash 全变"
    moduleIds: 'deterministic',
    chunkIds: 'deterministic'
  }
}
```

这不是什么性能优化秘籍，而是一种稳定性设计，让你的缓存系统在持续迭代下仍然可预期。

缓存层面我建议你明确一套分层模型，而不是只用 vendor 这个粗粒度概念。基础层，框架与基础设施，react、react-dom、runtime、polyfill、核心工具。生态层，变化较慢但会升级的库，UI 库、状态管理、可视化。业务共享层，项目内稳定的共享模块，设计系统、业务组件库、公共逻辑。还有业务层，路由、功能、页面本身。

分层的价值在于，你能把变化频率作为第一维度，把共享程度作为第二维度，来定义 chunk 边界。这样你的缓存失效更接近应该失效的部分失效，而不是什么都失效。你想想看，一个 UI 库的升级，凭什么要把 react 的缓存也一起废掉？

## splitChunks 的真实目标，减少重复与控制共享

splitChunks 常被误用成拆得更细的开关。坦率的讲，我自己以前也这么用过，觉得配置越多 chunk 越碎就越好。后来才慢慢理解，正确理解是它是一套共享策略，目标是控制哪些模块被提取为共享 chunk，避免被多个入口重复打包。控制共享 chunk 的命名与稳定性，避免边界抖动导致缓存失效。还有在性能与稳定性之间做权衡，并不是共享越多越好。

一个更接近工程实践的 splitChunks 配置，通常会显式表达分层，而不是只写默认配置。

```js
// webpack.config.js 片段：用 cacheGroups 表达"层"
module.exports = {
  optimization: {
    splitChunks: {
      chunks: 'all',
      // 避免在小改动下频繁触发边界重算（导致 chunk 变来变去）
      minSize: 30 * 1024,
      maxAsyncRequests: 20,
      maxInitialRequests: 20,
      cacheGroups: {
        // 框架层：尽量稳定
        framework: {
          test: /[\\/]node_modules[\\/](react|react-dom)[\\/]/,
          name: 'framework',
          priority: 40,
          enforce: true
        },
        // 生态层：UI/工具等，按你项目实际拆分
        libs: {
          test: /[\\/]node_modules[\\/]/,
          name: 'libs',
          priority: 20,
          reuseExistingChunk: true
        },
        // 业务共享层：你自己的稳定公共模块
        commons: {
          test: /[\\/]src[\\/]shared[\\/]/,
          name: 'commons',
          priority: 10,
          minChunks: 2,
          reuseExistingChunk: true
        }
      }
    }
  }
}
```

这里的核心不是 framework、libs、commons 这几个名字，而是三条工程原则。

分层优先。不要把所有 node_modules 统统塞到一个 vendor 里，因为它的变更频率与共享模式并不一致。稳定优先。对关键层比如 framework 用 enforce 和高优先级保证边界稳定，避免边界抖动。共享有界。共享不是越多越好，过度共享会增加初始化时必须下载的东西，反而拖慢首屏。

我之前带过一个项目，当时把 antd、lodash、moment 全塞一个 vendor 里，结果每次升级 antd 版本，整个 vendor 的 hash 都变了，全站缓存瞬间失效。后来拆成三层之后，antd 升级只影响生态层的 hash，基础层和业务层完全不动。那种感觉太爽了。

## 部署稳定性，把构建产物与发布动作当成一个系统

很多团队把代码分割只当作构建问题。但线上事故往往发生在部署系统。HTML 指向的 chunk 与 CDN 上实际存在的 chunk 不一致，动态加载就失败了。

你可能见过这些报错。Loading chunk xxx failed。ChunkLoadError。Failed to fetch dynamically imported module。

这类问题的根因通常不是代码写错，而是发布不是原子操作。典型场景是这样的。你发布了新 HTML 或者新入口 JS，它引用了新版本的 chunk。但 CDN 或者静态站点的 chunk 还没完全同步，或者旧版本 chunk 被清理了。用户拿到新 HTML，请求到的却是旧 chunk 目录或者不存在的 chunk，加载失败。

所以部署稳定性是缓存策略的一部分，你必须保证引用关系的一致性。工程上常见的做法有这么几种。

版本化目录，每次构建产物输出到带 buildId 的目录，HTML 只引用这次 buildId 下的资源。原子切换，HTML 的发布与资源目录的可用性要么同时生效要么都不生效。旧版本保留窗口，允许旧 buildId 资源保留一段时间，覆盖长尾用户与回滚窗口。

用伪配置表达这种策略。

```js
// 构建侧：把所有资源输出到带 buildId 的目录
module.exports = {
  output: {
    publicPath: `/assets/${process.env.BUILD_ID}/`,
    filename: 'js/[name].[contenthash:8].js',
    chunkFilename: 'js/[name].[contenthash:8].js'
  }
}
```

```nginx
# 部署侧（示意）：对带 hash 的静态资源使用长期缓存，对 HTML 使用短缓存或不缓存
location /assets/ {
  add_header Cache-Control "public, max-age=31536000, immutable";
}
location / {
  add_header Cache-Control "no-cache";
}
```

注意，这不是说你必须这样做。而是告诉你，部署稳定性必须与代码分割一起设计。否则你拆得越细，线上不一致的概率越高。回到开头那个朋友的例子，他的问题就是分割做了一堆，但部署完全没配套，结果 chunk 一多，引用关系一复杂，出错就是必然的事了。

## 如何衡量拆得好，可观测性与回归基线

代码分割的复杂度在于，它会随着业务增长、依赖升级、团队协作不断变化。你需要一套可观测体系，避免悄悄变坏。

我建议至少把这些指标纳入回归。初始 chunk 集的总下载体积，gzip 和 brotli 与原始体积都要看。初始 chunk 集的数量与并发请求峰值。framework、libs、commons、business 各层的体积与变更频率，谁在变大，为什么。同一模块是否被重复打进多个 chunk，重复体积有多少。还有 contenthash 级联程度，改一行业务代码，哪些 chunk 受影响。

在工程里你需要的是边界可解释性，而不是某一次构建看起来不错。可解释性通常来自命名清晰的 cacheGroups，统计输出以及固定的 budget，对关键入口建立性能基线，比如首屏 TTI 和加载瀑布图。

## 常见误区，把拆分当成银弹

顺着上面聊的，再说几个我见过的典型反模式。

### 反模式一，无差别动态 import 导致 chunk 数量爆炸

把每个组件都 dynamic import，会让请求数与调度成本快速上升。更糟的是边界过细会让共享抽取变得更复杂，最终你会得到大量小 chunk，网络和 CPU 都不友好。正确做法是只把生命周期差异显著的模块拆出去，路由级、重型依赖、低频功能。

### 反模式二，splitChunks 边界抖动导致缓存失效半径变大

常见触发器是过于激进的阈值与默认组。模块体积稍有变化 chunk 归属就改变，导致多个 chunk 的 hash 同时变化。你会误以为 contenthash 不稳定，其实是边界不稳定。用分层的 cacheGroups，提高稳定层优先级，能显著降低抖动。

### 反模式三，把所有依赖塞进一个 vendor 掩盖真实变化频率

一个大 vendor 看起来缓存友好，但它把变化频率差异巨大的依赖混在一起了。一次 UI 库升级可能导致 vendor 大改，造成全站缓存失效。分层拆分才能把失效控制在应该失效的那一层。

### 反模式四，忽略部署一致性导致 chunk load error 成为常态

当你做了大量异步 chunk 而部署不具备原子性，线上事故只是时间问题。拆分越多引用关系越多，不一致的概率越高。先把发布模型想清楚，再谈分割收益。

## 我的判断，把代码分割当作长期治理

我对代码分割的判断是，它更像一项治理能力，而不是一次性性能优化。真正可持续的策略通常具备三个特征。

以模块图为依据，边界来源于生命周期与变更频率差异，而不是大家都这么拆。以缓存与部署为约束，稳定性优先于极限性能，能回滚、可诊断、可预测，比某次首屏少 20KB 更值钱。以可观测为抓手，用统计与预算把边界固定下来，让系统在团队规模增长时仍然可控。

怎么说呢，当你把 chunk 当成发布和缓存单元，把 splitChunks 当成共享策略，把部署当成引用一致性系统，你会发现代码分割不再是玄学配置，而是一套可以持续迭代的工程设计。

回到开头那个朋友，后来他重新梳理了分层，把部署流程也配套改了，chunk load error 降到了原来的十分之一。他跟我说早知道就不急着拆那么碎了。

其实吧，工程这件事情，很多时候不是做得越多越好，而是想清楚再做。
