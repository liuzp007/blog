事情是这样的。前阵子有个同事跑过来找我，说他本地跑得好好的项目，换了台机器就炸了。dev server 启动倒是没报错，但页面一打开就看到 React hooks 报一大堆莫名其妙的错。他折腾了一下午，最后发现是某个依赖被预构建了两份。

然后他问我一个特别经典的问题，「那我把它加到 optimizeDeps.include 里是不是就行了？」

我当时就愣住了。不是因为他问得不对，而是因为这个问题实在太典型了。在 Vite 项目里，「遇到问题就调 optimizeDeps」几乎已经变成了一种条件反射。把某个包加进 include，把某个包塞进 exclude，然后祈祷。短期看，问题经常真的消失了。长期看，你会得到一个谁都不敢动的配置补丁集合，换机器炸，换分支炸，升级依赖还是炸。

我自己也踩过这个坑。所以我特别想聊一下这件事。不是教你「怎么配 optimizeDeps」，而是想跟你聊聊，这个东西到底在干什么，什么时候该碰它，什么时候不该碰。

坦率的讲，我自己花了很长时间才把这件事想明白。

## 预构建不是加速器，而是语义翻译层

说真的，很多人的第一反应是，预构建就是让 dev server 启动更快。这个理解不算错，但它会让你在决策的时候跑偏。

我自己的感受是，你把预构建理解成一层翻译机制，会更准确。

前端依赖生态现在是什么情况呢，ESM、CommonJS、UMD、条件导出、深层子路径导入、动态 require，这帮东西全部活着，全都有人在用。浏览器端的 ESM 是很严格的，它需要静态可解析的依赖关系和明确的 URL。dev server 也一样，它需要稳定的模块边界来构建 module graph，然后才能做 HMR 的失效边界。

那问题就来了，当依赖不满足这些条件的时候怎么办呢。Vite 必须做翻译，把不适合被浏览器直接消费的依赖，变成浏览器能消费、且可缓存的形式。这个过程通常靠 esbuild 之类的快速打包器来完成，输出一份在 dev 场景可复用的 ESM 产物。

一旦你把预构建理解成翻译层，你会得到两个我觉得挺重要的结论。

预构建的首要目标是确定性，同一份依赖在不同机器上、不同启动次数上，应该得到相同的翻译结果。而不是「这台机器跑得挺快的但换一台就不知道了」。

include 和 exclude 的首要目标是降低翻译歧义。当自动推断不可靠的时候，你手工告诉系统哪些依赖必须预构建、哪些必须跳过，换的是稳定性。

速度只是副产物。

## optimizeDeps 在 dev 中的角色

聊到这你可能会想，包管理器不是已经把依赖装好了吗，为什么 dev server 还要再折腾一遍。

这块需要注意一下。包管理器解决的是安装与版本解析，Vite dev server 解决的是模块加载与运行时一致性。这两件事的边界经常被搞混。很多人觉得只要 pnpm install 跑通了，dev server 就应该稳定。但事实上 dev server 的模块图构建比包管理器严格得多。

什么时候会出问题呢。

同一个包通过不同路径被引用，子路径导入、别名、条件导出都可能触发。monorepo 里存在 workspace 包的软链接与真实路径的差异。依赖在不同环境下输出不同入口，browser 和 node 条件、development 和 production 条件。依赖内部用了 require()，对静态分析完全不友好。

optimizeDeps 做的事，是把这些包管理层的模糊地带，尽量收敛成 module graph 的确定边界。你如果经常遇到同一个包在页面里出现两份实例，那不是 Vite 在搞随机，是边界没有被收敛。

## 依赖扫描的盲区

自动预构建通常从扫描入口开始。dev server 得先知道页面会用到哪些依赖。

但这里天然存在盲区。静态分析看不到运行时才出现的导入。

动态 import() 里的变量拼接，或者运行时才决定路径。依赖在某个分支内才会被导入，按平台、按权限、按环境都有可能。通过 JSON 配置、路由表、插件系统延迟加载的模块。

当盲区存在的时候，你会观察到一种很烦人的现象。第一次打开某个页面很慢，甚至直接报错。第二次打开就好了。

为什么呢。因为第一次访问触发了临时的转换与缓存，但它不稳定、不可预测，在某些机器上可能直接就失败了。

这时候手工 include 的价值就体现出来了。不是加速，是把盲区变成显式依赖，把「第一次访问的偶然行为」变成「启动时可解释的确定行为」。

```ts
// vite.config.ts（示意）
import { defineConfig } from 'vite'

export default defineConfig({
  optimizeDeps: {
    // 让扫描盲区中的依赖提前被翻译成稳定的 ESM 形态
    include: ['some-cjs-lib', 'legacy-umd-lib'],
    // 避免对带副作用的依赖做预构建（需要你明确知道为何排除）
    exclude: ['some-weird-bundled-lib']
  }
})
```

但关键不在于加了就好。你必须能解释为什么它属于 include 或者 exclude，否则这就只是未来的雷。

说真的，我见过太多项目的 vite.config.ts 里，optimizeDeps 配了一长串，但没有任何注释解释为什么加。新来的人不敢删，老人忘了为什么加。这玩意就变成了一个谁都不敢碰的黑箱。

## include 和 exclude 的原则

我一直觉得，做工程决策的时候，最怕的不是选错，而是不知道自己为什么这么选。

我建议把 include 看成稳定性白名单，把 exclude 看成风险隔离名单。决策的时候不要从快不快出发，而要从不确定性出发。

当一个依赖的入口解析不稳定，环境条件、exports 条件、子路径导入混乱，并且它是你的关键依赖，那就倾向 include。

当一个依赖本身已经是稳定 ESM，或者被预构建会导致副作用重复、全局状态被破坏，那就倾向 exclude。

当你无法解释它为什么需要 include 或者 exclude，先不要加，先定位根因。

有个高频误区我想提一下。很多人把 exclude 当成「跳过预构建就能解决一切」。实际上 exclude 往往是在承认，这个依赖不适合被 dev server 当作模块来服务。你选择把它留在原始形态，让浏览器或 transform 在运行时处理。它可能暂时绕开了某些问题，但也可能把问题推迟到了更难调试的地方。

怎么说呢，就像你家里有个漏水的水龙头，你不去修它，而是在下面放了个盆。盆满了你倒掉，继续放。问题没解决，只是延后了。

## 典型事故，双份依赖与符号不一致

在大型项目里，最贵的故障通常不是启动慢，而是那种「看着一切正常但行为诡异」的问题。双份依赖就是典型的这种。

同一个库在页面中出现两份实例。会导致什么呢。

React hooks 报错或者状态异常，因为页面里其实跑了两份 React。单例配置失效，你以为写进了 A 的配置，B 完全看不到。类型层面看起来一模一样，运行时却不相等，instanceof 失败，Symbol 比较失败。

这种问题往往由路径不一致触发。一个模块通过 node_modules 解析，另一个通过 workspace 链接路径解析。或者一个走了预构建产物路径，另一个走了源路径。

你如果只是删缓存来解决，它一定会复发。

工程上更可靠的做法是统一解析路径与依赖入口，确保同一个包只有一个真入口。这通常涉及几个方面。

统一别名策略，避免同包多路径。对 monorepo 包的依赖边界做约束，不要跨包深层引用未公开的子路径。必要时对关键依赖加 include，收敛为同一份预构建产物。

```ts
// 一个"路径不一致"的常见诱因（示意）
// A 包：import 'lib'
// B 包：import 'lib/dist/index.js'
//
// 这会让解析落到不同入口，进而触发两份实例或不同编译结果。
```

你需要把统一入口当成工程规范，而不是遇到 bug 才想起来。

这块我自己踩过大坑。有一次排查了整整两天，最后发现就是某个同事在 A 包里 import 'lib'，在 B 包里 import 'lib/dist/index.js'。两个入口。两份实例。一切诡异行为的根源就在这里。

## 典型事故，条件导出导致的环境分裂

很多包会在 package.json 里做条件导出，不同环境给不同入口。这本身没问题，问题在于环境的判断并不是你想象的那一个，尤其当工具链链路复杂的时候。

```json
{
  "name": "some-lib",
  "exports": {
    ".": {
      "browser": "./dist/browser.js",
      "default": "./dist/index.js"
    }
  }
}
```

在 dev 里你可能拿到 browser 入口，在 build 里拿到 default 入口，或者反过来。于是出现了那种让人崩溃的「dev 正常 prod 异常」的情况。

很多人第一反应是怪 Vite。但其实这不是 Vite 的问题，是条件导出带来的环境分裂没有被纳入你的工程假设。

这类问题怎么解呢，我的优先级顺序是这样的。

先在依赖层修复，明确你要哪个入口，避免隐式条件。再在配置层收敛，通过 resolve 条件、别名或者 optimizeDeps 让入口保持一致。最后才是补丁，在某个环境里写 hack，但这通常会留下技术债。

能不写 hack 就不写。

## monorepo 与 link，workspace 包到底是什么

在 monorepo 里，workspace 包的身份特别尴尬。它既像依赖又像源码。

你希望它像源码一样可以热更新、方便调试。你又希望它像依赖一样稳定、单一入口。这两个目标冲突的时候，团队经常靠加 include 或者 exclude 来调参。但如果没有原则，很快就会失控。

我的经验是把 workspace 包分两类来治理。

产品包，对外发布、版本语义明确、入口清晰的。尽量像依赖一样对待，入口稳定，避免深层引用。

源码包，内部复用、频繁变更、需要 HMR 的。尽量像源码一样对待，保持编译一致，避免被预构建吞掉源码语义。

当你把包分好类之后，optimizeDeps 才有了稳定的决策边界。你不会一会儿把它当源码一会儿当依赖，让预构建与 HMR 的行为在不同机器上随机漂移。

## 反模式，把 optimizeDeps 当补丁集合

这块我见过的反模式还挺多的，列几个最常见的。

只要报错就 include。你会把真正的入口不一致、条件导出问题掩盖掉。问题没消失，只是藏起来了。

只要变慢就 exclude。你会把预构建的稳定性问题推到运行时，制造更难复现的故障。

不记录原因。没有为什么加的注释或文档，新人无法判断能不能删，最终没人敢删。

每个包各自加。monorepo 里各个子项目随意覆盖 optimizeDeps，最后行为不一致，调试成本直接爆炸。

如果你只能修一条，我建议先修缺少原因记录这一条。因为 optimizeDeps 的配置不是代码，它更像系统参数。系统参数最怕没有解释。解释才是治理的起点。

## 把 optimizeDeps 当成稳定性预算

回到开头的问题。那个同事问我「加到 include 里是不是就行了」，我的回答是，可以，但你要先搞清楚为什么会出两份实例。如果你只是把它加到 include 里而不解决路径不一致的根因，下次换个场景它还会炸。

在成熟的团队里，optimizeDeps 的目标应该是让 dev server 的行为更确定，而不是让某台机器更快。你应该把每一条 include 和 exclude 都当成一笔预算。

你用手工干预换来了稳定性。

你也引入了维护成本。升级依赖时要复核，换构建策略时要复核，迁移 SSR 时还要复核。

所以最好的策略不是尽量少配或者尽量多配，而是只对不确定性最大的地方配，并且把原因写清楚。

当你能解释每一条配置的来源的时候，你的 Vite 才是可治理的。否则它只是更快地把不确定性带到你面前。

你觉得呢。
