事情是这样的。

去年有个团队找我帮忙看他们的构建问题，项目是一个上千模块的 monorepo，三个应用共享一套组件库。他们跟我说，刚切到 Vite 的时候简直像开了挂，冷启动从两分钟变成五秒，HMR 几乎是毫秒级的。但半年之后，情况就开始不对劲了。

某台机器快，某台机器慢。某个分支快，切个分支就卡住。某个页面快，另一个页面白屏。CI 偶尔失败，重跑又过了。清缓存就好，不清就出事。

他们问我，是不是 Vite 不适合大型项目？

我看了他们的代码，跟他们说，不是 Vite 的问题，是你们的项目没有治理。

我自己的感受是，很多人把 Vite 当成一个「更快脚手架」来用，觉得快就够了。坦率的讲，快只是红利期的表象，真正决定一个大型项目能不能长期跑得动的，不是启动速度，而是治理能力。

治理不是加更多规则，不是把所有东西都配置化。是把不可控变成可控，让性能有预算，让边界可观察，让问题可定位，让变化可回滚。

下面我不会重复那些「Vite 是 ESM dev server」的基础知识。我从大型项目真实的成本结构出发，讲讲你需要治理什么，怎么治理，哪些看似合理的做法其实会把你推向更大的坑。

## 大型项目的真实敌人，漂移、碎片化、不可诊断

小项目里的工程问题，多半是做不做的问题。大型项目里，更多是能不能稳定地做的问题。

Vite 在规模化场景里最常见的失败，不是因为某个配置项没写对，而是三个结构性敌人在作祟。

第一个叫漂移。同一个工程意图在不同环境、不同包、不同插件链里逐渐不一致。比如同样的 `@/` 别名，A 包能用，B 包不能用。同样的依赖，本地是 ESM，CI 里被预构建成 CJS 包裹。同样的环境变量，dev、build、preview 三个模式下语义各不相同。你想想看，一个团队里每个人跑出来的行为都不一样，这还怎么协作。

第二个叫碎片化。依赖层、模块层、Chunk 层过度碎片化，性能就开始抖。典型症状是什么，冷启动快，但页面切换慢。改一行代码，HMR 传播范围完全不可预测。或者因为「只按需」导致大量网络往返和解析成本反而上升了。

第三个叫不可诊断。问题出现的时候你根本不知道到底发生了什么。动态导入失败，chunk load error，某个页面只在某个路由组合下白屏。根因不是问题本身有多复杂，而是你缺少统一的可观察面。你没有可靠的依赖图视图，没有插件链视图，没有缓存命中视图，没有产物边界视图。

治理的目标就是把这三件事变得可控。接下来所有的建议都围绕这三个点，减少漂移，抑制碎片化，增强可诊断性。

## 配置不是文件，而是一份工程宪法

大型项目里最危险的不是没有最佳实践，而是每个人都有自己的最佳实践。

Vite 的配置入口真的很自由，`defineConfig`、`mode`、`envDir`、`plugins`、`resolve`、`server`、`build`、`optimizeDeps`，每个点都能实现同一个目标的不同版本。自由在小项目里是好事，在规模化的时候就是漂移的温床。

我一直觉得，Vite 的配置应该被当成一份「工程宪法」来对待。它应该明确划分三层东西。

第一层是不变的语义约束。别名、环境变量命名约定、import 规则、资产路径策略、polyfill 边界。这些东西在任何包、任何环境下都不应该不一致。

第二层是可被产品需求驱动的策略。分包策略、预加载策略、构建产物目录、source map 策略。这些可以随产品迭代调整，但调整要显式、要统一。

第三层是可随机器差异调参的参数。HMR overlay、server watch、cache dir、并行度。这些允许不同开发者有不同的本地偏好，但范围要受控。

一个可落地的办法是把配置拆成「基座配置 + 领域配置 + 包内配置」，并且限制包内配置只能在受控范围内覆盖。下面给一个可执行的骨架，示例以 monorepo 为例，你可以简化成单仓库。

```ts
// packages/build/vite.base.ts
import { defineConfig, mergeConfig } from 'vite'
import react from '@vitejs/plugin-react'
import path from 'node:path'

export function createBaseConfig(opts: { root: string }) {
  return defineConfig({
    plugins: [react()],
    resolve: {
      alias: {
        '@': path.resolve(opts.root, 'src')
      }
    },
    envPrefix: ['VITE_', 'APP_'],
    server: {
      // 大项目里优先保证一致性：不要让某些机器"看见"不同的文件变更
      watch: {
        ignored: ['**/dist/**', '**/.cache/**']
      }
    }
  })
}

export function mergeWithBase(root: string, cfg: any) {
  return mergeConfig(createBaseConfig({ root }), cfg)
}
```

在具体应用里你只允许在这个基座之上叠加「领域策略」，而不是随手在每个包里复制一份 `vite.config.ts`。这样做的工程收益不是说更好看，而是把漂移的可能性压到最小。别名不再漂移，envPrefix 不再漂移，插件基座不再漂移。

说真的，治理的第一原则就是先统一语义，再谈性能。否则你会得到一个很快但不一致的系统，这比慢但一致的系统更难维护。因为你不知道慢在哪里，也不知道快是不是偶然。

## 依赖治理，optimizeDeps 不是加速按钮，是闸门

Vite 的依赖预构建，也就是 optimizeDeps，在大项目里被误用的频率太高了。慢了就 include，报错了就 exclude，跟救火似的。

这种做法能短期止痛，但会制造长期隐患。双份依赖、符号不一致、热更新边界异常、某些包只在某些入口下能用，这些诡异的问题背后往往都是 optimizeDeps 被当成了旋钮而不是闸门。

在治理视角里，optimizeDeps 的定位应该是把依赖层从「历史模块规范与分发形态的混乱」翻译成「dev server 可稳定服务的模块形态」。它是一个闸门。闸门的治理目标是稳定和一致，不是追求某次启动快个两秒。

我建议在大型项目里把依赖分成三类，给不同策略。

基础依赖，就是 react、vue、router、state、ui 这些核心库。目标是单例与一致。策略是尽量避免多版本、多实例、多份打包，对它们的预构建策略应当尽量固定。

业务依赖，就是 date、request、charts、editor 这些常用工具。目标是稳定的 dev 形态。策略是用一次性治理把常见的 CJS 和 ESM 混用问题解决掉，而不是每次遇到都手动 include 或者 exclude。

边缘依赖，就是只在少数页面用到的库。目标是尽量不污染全局预构建。策略是按需加载，接受首次使用的成本，别让它们把全局缓存搞脏。

下面是一段更像「治理」而不是「救火」的配置示意。关键点不是配置本身，而是每条规则旁边的注释。你要让未来的人能回答「为什么这条规则存在」，否则规则会变成迷信集合。

```ts
// vite.config.ts 片段
export default defineConfig({
  optimizeDeps: {
    // 目标：统一基础依赖的 dev 形态，避免多实例与符号不一致
    include: [
      'dayjs',
      // 如果 UI 库存在深层 CJS 入口，这里显式纳入，保证预构建稳定
      'antd/es'
    ],
    // 目标：不要把 Node-only 或条件导出复杂的包拖进预构建
    exclude: [
      // 这些包要么依赖 Node API，要么会在预构建阶段走到错误分支
      'fsevents'
    ]
  }
})
```

依赖治理还有一个经常被忽视的点，就是锁定依赖解析的唯一性。在 monorepo 里，同一个依赖可能在不同 workspace 下被解析到不同路径，看起来版本一样但实例不同。这会直接破坏 React 或者 Vue 的单例假设，造成极其诡异的运行时错误。

坦率的讲，如果你看到 hooks 报错、context 断裂、样式重复注入、HMR 只对某些包生效，第一时间不要怀疑业务代码，先怀疑依赖唯一性。这个判断能帮你省掉大量排查时间。

## 插件治理，插件链就是你的编译器

在大型项目里，插件不是「可选增强」，插件链就是你的编译器。编译器如果不可审计，你的系统就不可诊断。

很多团队的插件失控有三种表现。

第一种，插件越来越多，但没人知道每个插件在 dev、build、ssr 哪个阶段生效。

第二种，插件顺序靠运气。某次升级把顺序改了，产物语义变了但 CI 没抓到。

第三种，插件偷偷做了语义变更。比如把某些 import 改写了，把环境变量注入了，把 CSS 处理方式改了，导致 dev 跟 prod 分叉。

治理建议是把插件分层，并且引入审计输出。你至少要能在构建日志里回答三个问题，这次启用了哪些插件，版本是什么。插件顺序是什么。哪些插件只在 dev 生效，哪些只在 build 生效。

你不需要上来就搞什么复杂的可视化，做一个简单的插件清单输出就行，并且把它作为 CI 的一部分。当插件链变化的时候，你应该像对待依赖变更一样对待它，可见、可 review、可追溯。

还有一条硬约束，禁止插件在 dev 阶段偷偷改变生产语义，除非它同样在 build 阶段生效并被验证。这句话听着有点抽象，但落地标准很简单。如果某个插件影响了 import 解析、代码转译结果、宏替换、CSS 注入顺序、asset url 重写，那它必须同时覆盖 dev 和 build，并且必须有可验证的回归，哪怕是最简单的 smoke test。

## 速度治理，把快变成预算而不是感觉

「快」在大型项目里需要被量化。否则就永远在争吵。有人说本地快，有人说 CI 慢。有人说首屏快，有人说切页慢。有人说冷启动快，有人说 HMR 抖。

治理的方式是建立预算。不是 KPI 啊，是工程预算。你至少需要三类预算。

开发预算。冷启动时间，HMR 更新延迟，首次打开某个关键页面的时间。

构建预算。全量构建时间，增量构建时间，产物大小含 gzip，以及缓存命中率。

运行预算。首屏 JS 体积，关键交互路径的长任务比例，chunk 数量范围。

预算的关键是可比较。你不需要一开始就上什么完整的监控系统，但至少要在 CI 里把关键指标输出出来，变更明显的时候 fail 掉。否则优化永远只能靠体感，而体感是最不可靠的东西。

更重要的是，预算要跟治理对象挂钩。

如果 HMR 变慢，你要能定位是插件链变慢了，还是依赖预构建失效了，还是 watcher 过量了。

如果构建变慢，你要能定位是 rollup 输出阶段的问题，还是 minify 的问题，还是 source map 的问题，还是某个插件的 transform 拖了后腿。

如果运行时 chunk load error 增多了，你要能定位是分包策略导致 hash 级联，还是部署窗口期不一致。

没有这个挂钩，预算就只是数字。

## 分包与产物治理，chunk 不是切得越细越好

大项目里「快」的另一个陷阱是，为了让首屏更小，拆出越来越多的 chunk。为了让缓存更好，抽出越来越多的 vendor。最后你得到了一个 chunk 数量爆炸、加载时序复杂、部署窗口期极易出错的系统。

不是哥们，这不是优化，这是给自己埋雷。

治理视角里，chunk 的核心价值是控制三件事。

下载与解析的时序复杂度。请求数越多，网络和 CPU 的不确定性越大。

缓存失效半径。变更频率不同的代码应该分离，否则一次改动会让大块缓存失效。

故障域与回滚半径。当某个 chunk 加载失败时，影响应当可控且可诊断。

所以你需要把分包策略从优化技巧提升为发布策略。在 Vite 也就是 Rollup 里，一个可治理的做法是把 `manualChunks` 设计成稳定的策略，避免随意按路径碎分。下面是一个偏治理的示意，不追求最优，只追求稳定和可解释。

```ts
// vite.config.ts 片段
export default defineConfig({
  build: {
    sourcemap: true,
    rollupOptions: {
      output: {
        manualChunks(id) {
          if (id.includes('node_modules')) {
            // 稳定切分：基础框架、UI、工具库分开，减少级联失效
            if (id.includes('/react/') || id.includes('/react-dom/')) return 'framework'
            if (id.includes('/antd/')) return 'ui'
            return 'vendor'
          }
          // 业务侧尽量按路由/领域切分，而不是按文件夹碎分
          if (id.includes('/src/pages/blog')) return 'page-blog'
          if (id.includes('/src/pages/home')) return 'page-home'
        }
      }
    }
  }
})
```

注意，这个策略的价值不是说更快，而是更稳定。当你发现 vendor 频繁变化时，你有可治理的路径，把变化频繁的三方依赖从 vendor 中抽出来。当你发现某个页面 chunk 过大时，你有可治理的路径，拆分页面内部的边缘能力，而不是把整个页面拆碎。

## 缓存治理，开发缓存和构建缓存要分开设计

大型项目里缓存是把双刃剑。命中时让你觉得世界美好，失效时让你怀疑人生。

Vite 的缓存包括依赖预构建缓存、transform 缓存、浏览器缓存。如果没有治理，会出现几个特别经典的症状。

我这台机器能跑，你那台不行。换分支就报错，清缓存就好。CI 偶尔失败，重跑就过。

这些症状说到底都是缓存失效语义不清晰。治理的关键不是让缓存更强，而是让缓存可预测地失效。

当 lockfile 变化时，依赖预构建缓存必须失效。当 Vite 版本或关键插件版本变化时，transform 缓存必须失效。当构建参数比如 mode、define、target 变化时，产物缓存必须失效。

如果你在 CI 里做缓存，必须把这些失效条件编码进 cache key。否则你缓存的不是一个可复用的构建结果，而是某种偶然可用的状态。

在团队层面你还需要规定一个统一的清理入口。不要让每个人各自记忆 `rm -rf node_modules/.vite`、`rm -rf dist`、`pnpm store prune` 这些命令。这也是治理，把经验变成机制。

## 常见误区与反模式

这一节我只列真正会在大项目里造成长期伤害的反模式。它们往往在短期看起来解决了问题，但会积累不可见的债务。

第一个，把 optimizeDeps 当成救火清单。每次遇到依赖问题就加 include 或者 exclude，最后变成一份没人敢动的配置清单。正确做法是先归因，是多实例问题还是条件导出问题还是包本身分发形态问题，然后用更稳定的方式修复，锁版本、统一入口、替换依赖、或者把边缘依赖隔离。

第二个，插件在 dev 中偷偷改变语义。某个插件为了开发方便改写 import、注入全局变量、改 CSS 顺序，但 build 阶段没有同等行为。结果 dev 跟 prod 分叉，bug 只在 prod 出现。正确做法是让语义变更在 dev 和 build 之间一致，并且建立最小验证。

第三个，分包按路径碎切。为了更细的按需加载，把 `manualChunks` 写成按目录切片。结果 chunk 数量爆炸、hash 级联、部署窗口期更容易出现 chunk load error。正确做法是按变更频率加共享程度加生命周期做分区。

第四个，把快当作唯一目标。为了启动快关闭 sourcemap、关闭类型检查、关掉关键校验。短期确实快了，长期排障成本飙升。正确做法是预算化，给开发、构建、运行三类预算，并且明确哪些指标必须守住。

第五个，允许包内随意覆盖基座配置。每个包各自写一份 `vite.config.ts`，别名、define、envPrefix 各自发挥。结果就是漂移和不可诊断。正确做法是基座配置统一语义，包内仅允许在受控范围扩展。

怎么说呢，这些反模式的共同点是它们把系统性问题变成了配置堆叠，把治理成本从一次性变成了永久性。

## 我的判断，Vite 的第二阶段是治理不是速度

我对大型项目使用 Vite 的判断可以概括成几句话。

Vite 的第一阶段红利来自架构选择，ESM dev server。第二阶段的长期收益来自治理设计。如果你只享受第一阶段红利，你会在规模化后把红利吐回去。

治理的核心不是更多配置，而是更少漂移、更少碎片化、更强诊断。任何方案只要不能让问题更可解释、更可回滚、更可验证，就不算治理。

把 Vite 当成编译器来管理，而不是当成脚手架来使用。编译器需要规则、边界、审计和预算。你不需要复杂的工具，但你必须有明确的系统观。

最后给一个可执行的落地顺序，不是清单，是优先级。

先统一语义，base config 加 envPrefix 加 alias 加插件基座。再治理依赖唯一性和 optimizeDeps，稳定比快重要。再治理分包策略，可解释比细碎重要。最后才是细项优化，并行度、cache、个别插件提速。

当你按这个顺序推进，你会发现速度不再是一种运气，而是一种可以长期维持的工程属性。

这不是什么高深的东西，但你不做，它就会在某个深夜以你意想不到的方式炸给你看。
