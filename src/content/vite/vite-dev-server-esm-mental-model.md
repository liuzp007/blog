事情是这样的。上周有个同事跑过来跟我讲，他们团队打算把一个 webpack 项目迁移到 Vite，理由特别简单，就一个字，快。我当时听完没接话，不是觉得这个方向不对，是我心里在想，你确定你理解这个「快」到底快在哪吗。

很多团队聊 Vite 就只聊快，好像这个词本身就是答案。但快是一个被滥用的评价词，坦率的讲，它甚至会误导决策。你得把快拆成能度量的时间尺度，才能判断它在你的代码库里到底是收益，还是把问题从构建期挪到了运行期，从一次性挪到了长期维护。

我自己写这篇文章的想法也很直白，把 Vite 的优势来自哪里讲清楚，同时把代价摊开讲，两边你都得接受，才能把它用成生产力工具。

## 快的定义，把体验拆成四个时间尺度

说真的，如果你只问「启动快不快」，你会得到一个特别片面的答案。更有用的做法是把开发体验拆成四类时间尺度来看。

冷启动，第一次启动 dev server 到页面首屏可交互。热启动，改一行业务代码到页面刷新或热更新完成。切页与懒加载，从一个路由切到另一个路由，首次访问某个按需加载模块的等待。还有退化场景，依赖升级、锁文件变化、node_modules 重装、分支切换之后，性能是否稳定，会不会突然变慢。

Vite 的优势集中在热启动和切页这两块。它把全量重打包变成了按需编译和按需传输，你改动的范围越小、依赖图越局部，收益就越明显。但冷启动和退化场景的体验，取决于预构建、缓存命中和网络条件，很容易被错误的配置和糟糕的工程治理给抵消掉。

## ESM Dev Server 的关键机制，把编译拆成可请求的资源

回到这块。传统打包器的开发模式是这样的，把模块图整体打成一个或多个 bundle，然后让浏览器去加载这些 bundle。你只改了一个组件，开发服务器也往往要经历重建整个输出的过程，区别只在于重建快不快。

ESM dev server 的思路完全反过来了。浏览器天然就懂 import，那就让浏览器按模块去请求资源，开发服务器只在被请求的时候把模块转换成浏览器可执行的形式，并且把依赖重写成指向 dev server 的路径。

你在浏览器里看到的不是一个打包产物，而是一串模块资源的按需请求。Vite 的快，首先来自把构建拆成了服务化的 transform。

我自己的感受是，这里有个特别有意思的思维实验。同样是入口引用 3 个模块，传统 bundle 是 1 次请求，ESM dev server 是 1+N 次请求，但只在需要时编译需要的模块。

```ts
// main.ts
import { createApp } from './app'
import './style.css'
import { initTelemetry } from './telemetry'

createApp()
initTelemetry()
```

如果 telemetry 在某个环境条件下不会运行，ESM dev server 模式可以在路径、条件和动态 import 的设计上把它推迟，缩小编译与加载的即时范围。

```ts
// main.ts
import { createApp } from './app'
import './style.css'

createApp()

if (import.meta.env.DEV) {
  import('./telemetry').then(m => m.initTelemetry())
}
```

注意，这不是懒加载的胜利，而是边界可见之后你可以主动选择边界。Vite 让这种边界变得更自然，但到底该不该这样拆，依然是工程判断。

## 模块图、失效边界与 HMR，为何局部更新不是免费午餐

顺着上面的再聊聊 HMR。

HMR 的核心不是把代码打补丁，而是知道补丁的影响范围。影响范围的最小单位就是模块，影响范围的计算依据就是依赖图，module graph。

当你修改一个模块的时候，dev server 需要回答三个问题。哪些模块依赖了它，这是上游。哪些模块被它依赖，这是下游。这次改动能不能在不刷新页面的情况下被接受，这就是 accept boundary。

Vite 的 HMR 体验通常很好，我觉得原因在于 ESM 模块边界加上框架插件的组合下，边界更容易被建立。组件模块往往能自洽地 accept 更新，样式模块可以天然地热替换，而且大多数变更都集中在业务组件树的叶子上。

但这里有个常被忽略的成本。模块边界越细，依赖图就越大，依赖图越大，失效传播的计算就越频繁。如果你在一个大型 monorepo 里不加约束地使用深层级动态 import、跨包互相引用、在模块初始化阶段做大量副作用，HMR 可能反而更不稳定。

表现是什么呢。同一处改动在不同机器上触发不同程度的刷新。某些模块更新后状态丢失、事件重复绑定、资源重复初始化。热更新链路变长，最后直接回退到整页刷新。

这不是 Vite 的锅，而是边界可见之后你需要对边界负责。模块化的收益来自边界，痛苦也来自边界。

## 冷启动并非总是快，预构建与缓存命中才是关键

说到这个，很多人第一次用 Vite 会惊叹秒起。但你在一个中大型项目里能不能稳定保持秒起，得看两个条件。

依赖预构建是否稳定，尤其是 CommonJS 依赖、多入口扫描、monorepo 链接依赖。以及缓存是否高命中，node_modules、预构建产物、transform 缓存、浏览器缓存、HTTP 缓存头，这一整条链路。

怎么说呢，冷启动快不是 ESM 自带的，而是 ESM 加预构建加缓存命中的组合拳。你如果把缓存当成不可控因素，团队的体验就会呈现很强的机器差异。某些同事永远快，某些同事永远慢，然后大家开始用删缓存、重装依赖、加 --force 来解决问题，最后把本来应该治理的系统问题变成了个人运维。

这里我想给一个工程化的建议。把冷启动拆成可观测步骤，写进团队 SOP，而不是只在 README 里写一句「慢了就删缓存」。

```bash
# 示例：排查思路（命令仅做示意）
pnpm dev -- --debug

# 观察：
# 1) 依赖预构建是否频繁发生
# 2) 预构建发生的原因是否是 lockfile 变化、路径变化或 include/exclude 策略不稳定
# 3) 哪些依赖在预构建阶段耗时最久
```

你不需要把每一次慢都解决掉，但你需要把慢的原因从玄学变成可解释的工程事实。

## 隐藏成本一，网络瀑布与模块碎片化

这块需要注意一下。ESM dev server 把 bundle 拆成模块请求，天然就更依赖网络条件。在低质量网络或者高延迟代理环境下，模块碎片化会导致瀑布式请求的体感退化。即便 HTTP/2 和 HTTP/3 能缓解连接开销，调度与队头阻塞仍然存在。

更现实的问题是，你越追求细粒度边界，就越容易产生大量小模块。小模块本身不是坏事，但当你没有规则地拆分时，后果就很明显了。一个页面首屏需要加载的模块数量膨胀，冷启动体感变差。变更触发的 HMR 链路更长，更频繁地回退到刷新。团队对「为什么这次热更新没生效」缺乏解释模型。

工程上的应对不是回到打包器时代，而是建立边界规则。哪些模块适合细拆，哪些模块应该聚合，哪些副作用必须延迟执行，这些东西得有共识。

## 隐藏成本二，开发与生产差异是一种债，不是缺陷

再聊聊另一个经常被低估的问题。

Vite 的 dev 和 build 不是同一条链路。dev 更接近 transform server，build 更接近 Rollup 打包产物。这会带来一个关键事实，你在 dev 里观察到的模块形态、加载顺序，甚至某些条件分支，可能跟 production 不完全一致。

这不是 bug，而是架构选择的结果。你应该把它当成债，用制度来管理它。

关键路径必须在生产构建产物上验证，至少在 CI 上做 smoke。对依赖边界敏感的改动，比如包导出、条件导入、SSR 分支，必须有最小可复现的测试页或脚本。对于只在 dev 出现的行为，比如某些动态 import 时机，你要明确这是允许的差异还是需要消除的差异。

当你把差异当成债，你就会自然地追问，债的利息是谁在付。如果利息主要由新人承担，比如新人经常问「为什么线上跟本地不一样」，那治理优先级就应该更高。

## 反模式，把 Vite 当成零配置黑盒

常见误区我建议你至少警惕这几条。

看到慢就加 --force，它会掩盖依赖预构建不稳定的根因，让团队长期付出冷启动成本。无约束地引入动态 import，把按需当成默认策略，最终演变为不可理解的加载拓扑。在模块顶层做重副作用，包括单例初始化、注册全局事件、启动定时器、读取环境配置，HMR 下很容易重复执行。还有把开发快当作唯一目标，忽略了生产构建、部署缓存与长期维护的成本函数。

如果你只能修一个，我建议从顶层副作用入手。它是 HMR 不稳定与运行时奇怪行为的最大来源之一，而且修复通常意味着把初始化从导入时执行变成显式启动，这会提升可读性与可测试性。

## 我的判断，Vite 的价值在于让边界可见，而不是让一切更快

最后一部分聊点我自己的判断。

我一直觉得，Vite 的长期价值不是速度，而是逼迫你正视模块边界。当边界可见，你可以用结构化的方式做三件事。

把开发体验从全量重建变成局部更新，并且把局部的定义写进代码结构。把依赖与缓存从玄学变成可治理对象，用策略来保证稳定。把 dev 与 prod 的差异从踩坑故事变成团队共识的债务清单，持续清偿。

如果你的团队愿意为边界负责，Vite 会把收益放大。如果团队只想要一个更快的脚手架，那它只会把问题换一种形式更早暴露出来。

选择它之前，先选择你要的工程文化。

你想清楚了吗。
