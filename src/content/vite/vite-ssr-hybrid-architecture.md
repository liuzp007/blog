事情是这样的。

去年有个朋友的项目上线了 SSR，团队开开心心地搞了两周，结果上线的第一天就翻车了。不是渲染崩了，是 hydraton mismatch，用户看到页面闪了一下，然后整个交互就废了。他们花了三天排查，最后发现问题出在一个组件里偷偷用了 window.innerWidth。

我当时就愣住了。

就一个 window，就能把整个 SSR 的心血给废了。说真的，从那以后我对 SSR 的态度就变了，它不是一个「你选不选」的技术选型题，它是一个「你的代码库够不够干净」的工程治理题。

很多团队把 SSR 当成一个开关，好像打开它，SEO 和首屏就自动变好了。坦率的讲，真正落地之后你才发现，SSR 逼你回答的全是你以前可以糊弄过去的问题。你的代码能不能在 Node 和浏览器里都稳定跑，你的数据是从哪取的，你的缓存策略是什么，这些东西在纯 CSR 的时候你可以装作看不见，SSR 一开，全给你翻出来。

这篇文章我想聊的就是这个事。标题那句话是我自己的真实感受，工程组织比 API 选择更关键。Vite 在 SSR 场景里给你的是编译能力和模块加载能力，它不会替你画边界。你边界清晰，Vite 的灵活性就是你的优势。你边界混乱，Vite 的灵活性只会让混乱加速扩散。

## 先把概念捋清楚

说到渲染方式，CSR、SSR、SSG、ISR 这些词天天被人挂在嘴边，但我发现很多人其实没真正理解它们在工程上到底有什么不同。不是概念有多难，是大家习惯把它当成一个标签，而不是一套约束。

我自己的感受是，每一种渲染方式对应的是一套「你怎么组织代码、组织数据、组织缓存」的约束集合。

CSR 最简单，浏览器拿到一个壳和 JS，数据在客户端拉，渲染在客户端完成。服务端轻松，但首屏和 SEO 你得额外想办法。SSR 是服务端在请求时就把 HTML 生成了，至少首屏是服务端渲染的，客户端再 hydration 接管交互。首屏快了，SEO 也有了，但运行时边界变复杂了，缓存策略变复杂了，成本也上去了。

SSG 是构建时就生成 HTML，请求来了直接返回静态文件，稳且便宜，但数据有延迟，动态性受限。ISR 是在 SSG 基础上加了个增量更新的能力，算是折中方案，但系统复杂度也跟着上来了。

你可能会问，那混合渲染又是什么鬼。

其实吧，混合渲染不是一个新技术名词，它就是一个工程选择，不同页面甚至不同片段用不同的策略。比如你的列表页用 SSR，因为首屏要快且要被搜索引擎收录。详情页用 SSG，因为内容稳定。评论区用 CSR，因为交互性强、延迟可接受。头部导航 SSR 输出，3D 那种重组件就 CSR 延迟加载。

混合渲染的难点从来不是「能不能做到」，而是「能不能治理」。如果每个页面都随心所欲地选策略，你会得到一个完全不可预测的系统。如果你把策略变成可配置、可回归、可演进的规则，你才算真正掌控了它。

## Vite SSR 到底给了你什么

回到 Vite SSR 这块，它的一个关键特征是「开放」。

怎么说呢，它不会强迫你用某个路由约定，不会强迫你用某个数据获取协议，不会强迫你用某个渲染生命周期。它给你的是什么呢，在 dev 阶段，按需编译和模块加载，你可以在 Node 侧直接加载 TS 和 JSX 源码，还保持 HMR 体验。在 build 阶段，产出 SSR bundle 和 client bundle，manifest 和静态资源映射你都能控制。

开放意味着自由。

但也意味着你必须自己回答几个要命的问题。

你的入口是什么，服务端入口和客户端入口怎么共享路由和渲染树。你的数据层在哪，数据是在服务端取还是客户端取，缓存怎么做。你的边界在哪，哪些模块只在服务端跑，哪些只在浏览器跑，哪些必须同构。

坦率的讲，如果你没法清晰地回答这些问题，SSR 会把你以前在 CSR 时可以忽略的问题全部给你放大。不是一点点放大，是成倍放大。

## 同构代码的坑，比你想象的深

顺着上面的再聊聊同构代码这个事。

很多 SSR 的故障都来自一个简单的误会。大家觉得同构代码就是「Node 能 import，浏览器也能 import」，就行了。说真的，差远了。同构代码是「在两个 runtime 下执行语义一致，至少差异是可解释的」。

哪些东西会破坏同构性呢。

依赖浏览器全局的，window、document、localStorage、matchMedia，这些一碰就炸。依赖 Node 全局的，process、fs、path、Buffer，也是一碰就炸。还有那种更阴险的，依赖时间和随机的。Date.now 和 Math.random 在 SSR 首屏会把输出变成不确定的，直接导致 hydration mismatch。还有一种就是环境分支的条件不一致，比如 dev 和 build 和 ssr 的条件导入不同，导致服务端和客户端渲染树不一样。

我自己的感受是，工程治理上你应该把代码按三个层级分区，而不是按「是不是 SSR」粗暴地二分。

shared 目录，严格同构，两端都能跑，只允许依赖少量纯函数库。server 目录，仅服务端，允许 I/O、缓存、鉴权。client 目录，仅浏览器，允许 DOM、交互、浏览器 API。

更重要的是制度。对 shared 目录你得更苛刻，宁可少放，也不要混入运行时依赖。SSR 最怕的就是「偶尔混进去一个 window」，因为这种 bug 往往只在某些路径触发，你本地很难稳定复现。等你上线了才发现，用户已经看到白屏了。

## 数据边界和渲染边界必须对齐

回到数据这块，SSR 里最贵的不是渲染本身，而是渲染依赖的数据。

你想想看，如果数据获取散落在组件里，缓存根本没法体系化。你不知道数据能不能共享，不知道能不能按路由粒度复用，更不知道服务端和客户端会不会重复请求。

一个更可治理的模式是把数据获取和渲染绑定到同一个「路由单元」上。每个路由定义一个 loader，它只负责返回渲染所需的最小数据。渲染函数只消费 loader 的结果，不直接发请求。

这不是为了写得「像某个框架」，而是为了让你能明确几件事。

缓存 key 应该是什么，通常是路由加参数加用户态。缓存 TTL 应该怎么定义，内容页长一点，用户页短一点。哪些数据允许在客户端复用，就是 hydration 注入的那些。哪些必须在客户端二次请求，比如涉及安全或个性化的。

下面给一个极简的路由 loader 加 SSR 渲染的示意，注意它强调的是边界，不追求完整框架化。

```ts
// server/router.ts（示意）
export type LoaderCtx = { url: string; headers: Record<string, string> }
export type LoaderResult = { status?: number; data: unknown; cacheTtlMs?: number }

export interface RouteDef {
  match: (url: string) => boolean
  load: (ctx: LoaderCtx) => Promise<LoaderResult>
}

export const routes: RouteDef[] = [
  {
    match: url => url.startsWith('/main/blog'),
    load: async () => ({ data: { kind: 'blog-list' }, cacheTtlMs: 10_000 })
  }
]
```

```ts
// server/ssr.ts（示意）
import { renderToString } from 'react-dom/server'
import { routes } from './router'
import App from '../src/App'

export async function handleRequest(url: string) {
  const route = routes.find(r => r.match(url))
  const loaded = route ? await route.load({ url, headers: {} }) : { data: null }

  const html = renderToString(<App />)
  // 把数据注入到 HTML 里，客户端 hydration 时复用，避免重复请求
  const state = JSON.stringify(loaded.data).replace(/</g, '\\u003c')
  return `<!doctype html>
<html>
  <head></head>
  <body>
    <div id="root">${html}</div>
    <script>window.__SSR_DATA__=${state}</script>
  </body>
</html>`
}
```

关键点不是代码长什么样，而是数据来源是可定位的。这样一来，缓存、鉴权、灰度这些事情都能落到同一个入口，而不是散落在组件树的各个角落。

## dev 和 build 的差异，在 SSR 下会变成线上事故

说到这个，有个事必须得提。

在纯 CSR 项目里，dev 和 build 的差异很多时候就是性能差异，慢一点快一点而已。但在 SSR 项目里，这种差异会演变成真正的线上事故。

dev 能跑，build 后服务端启动失败，因为依赖打包方式不同。dev hydration 正常，线上 hydration mismatch，因为代码分支不同、数据注入不同、序列化有差异。dev 只有单进程，线上多进程多实例，你在内存里缓存了不该缓存的东西，缓存不一致了。

Vite 的 dev 侧更接近「加载源码并转换执行」，build 侧更接近「打包产物并执行」。这两个模式的差异，你必须把「差异可回归」当成工程目标。至少得有一个最小的 SSR 产物 smoke 测试，确保 build 产物能启动并渲染关键路由。

如果你团队没有这个约束，SSR 会非常脆弱。每次升级依赖、升级 Vite、改个插件，都会带来不可预测的线上风险。最后大家会把 SSR 视为「难以维护的黑科技」。

不是 SSR 的问题，是工程纪律的问题。

## 混合渲染的正确姿势，先用成本函数驱动

混合渲染最怕的就是「随心所欲」。

我建议你用成本函数来驱动策略选择，而不是用技术偏好来驱动。一个可用的成本函数至少得包括这几个维度。

首屏价值，首屏快对你的业务是否关键，内容站通常很关键。个性化程度，页面是否强依赖用户态，强依赖的话 SSR 缓存复杂度飙升或者收益直接下降。更新频率，内容是否稳定，稳定的话 SSG 加长缓存收益巨大。交互密度，交互是否重，重交互往往客户端更合适。运行成本，你能接受多少服务端 CPU、内存、带宽开销。

有了成本函数，策略选择会变得很自然。

内容稳定且首屏价值高，那就 SSG 或者 SSR 加长缓存。内容变化快但可缓存，SSR 加短 TTL 再配个后台刷新。强个性化的页面，CSR 或者 SSR 只渲染壳，核心数据客户端请求。重组件比如 3D 和可视化，客户端延迟加载，SSR 只输出个占位。

混合渲染的工程目标从来不是「每个页面都最优」，而是「整体成本可控、行为可解释、策略可演进」。

## 没有缓存策略的 SSR，就是在烧钱

顺着上面的再聊聊缓存。

SSR 的成本主要来自两个方面，渲染和数据获取。你如果不做缓存，SSR 很快就会变成「把 CPU 当带宽用」的系统。每个请求都在做同样的渲染、同样的数据查询，即便你的页面渲染很快，数据层也会成为瓶颈。

我一直觉得应该把缓存分成三层来治理。

第一层是数据缓存，接口响应或聚合数据的缓存，粒度更细，复用性更强。第二层是片段缓存，某些可复用片段比如导航、页脚、部分组件树的缓存。第三层是页面缓存，整页 HTML 的缓存，收益最大但失效也最难。

很多团队一上来就搞整页缓存，结果发现处理不了用户态、A/B 测试、权限差异，最后又退回来了。我自己的感受是，更稳妥的路径往往是从数据缓存开始。它不依赖 HTML 结构，一致性更容易保证。等你把数据缓存稳定下来了，再考虑页面缓存就顺理成章了。

缓存还有一个经常被忽视的点，失效策略必须可解释。尤其是混合渲染场景，你很容易出现「列表是新数据，详情是旧数据」这种体验割裂。解决方案不是把所有 TTL 都缩短，而是把数据和页面的依赖关系写清楚，确保关键链路的失效边界是一致的。

## 那些年我见过的 SSR 反模式

这块需要注意一下，几个常见的误区和反模式我真的建议重点警惕。

第一个，把 SSR 当成 SEO 开关。只要能输出 HTML 就行，不管数据、缓存和一致性。结果首屏看起来确实快了，但线上成本爆炸而且经常 mismatch。

第二个，在组件里随意请求数据。服务端请求一次，客户端 hydration 后再请求一次，重复开销加闪烁。

第三个，同构代码里偷用浏览器 API。通过 typeof window !== 'undefined' 到处打补丁，最后 shared 代码不可测试也不可推理。

第四个，用内存单例缓存当全局缓存。本地 dev 没问题，上线多实例后缓存命中率下降且行为不一致，甚至缓存了用户态导致数据串号。

第五个，只在 dev 验证 SSR。不做 build 产物验证，上线才发现某个依赖打包后没法在 Node 里跑。

说真的，如果你只能改一条，我建议改「组件内请求数据」这个。它是 SSR 体系化失败的根源之一。它把数据层从一个可治理的入口分散到组件树里，缓存和一致性都会跟着崩坏。

## 边界可治理，才是 SSR 成功的关键

回到主线。

SSR 的价值来自把首屏和索引能力变成系统能力，但它的成本来自把运行时边界和数据边界强行暴露出来。Vite 给了你非常强的灵活性，但灵活性不是免费的，它要求你用工程组织来换取确定性。

如果你要在团队里长期维护 SSR 或者混合渲染，我建议你优先做三件事。

定义并守住目录边界，shared、server、client，让违规变得显而易见。把数据获取从组件树中抽离到路由单元或等价层，让缓存和鉴权有入口。建立 build 产物的最小回归，至少能启动、能渲染关键路由、能通过 hydration 的一致性检查。

做到这三点之后，API 选择反而变成细节了。你可以用 Vite 的 SSR 能力，也可以迁移到更框架化的方案，工程骨架不会变。

反过来，如果骨架不存在，任何 SSR 方案都会在复杂度面前迅速失控。

你准备好回答那三个问题了吗。
