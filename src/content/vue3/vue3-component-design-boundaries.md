去年有个朋友跟我说，他们团队的组件库改一个按钮组件要开两天会。我当时觉得夸张，后来仔细问了问，发现不是按钮复杂，是按钮里塞了权限判断、AB实验分流、国际化兜底、点击埋点（当然你们项目不用埋点），还有三种尺寸和五种主题的排列组合。谁都不敢改，因为没人知道改了会不会炸。

坦率的讲，这种事在中大型项目里太常见了。大家一开始的想法都很好，写个通用组件，以后所有业务都能复用。但通用这个词本身就有毒，它暗示你要覆盖所有场景，于是配置越来越多，分支越来越密，组件越来越像一个伪装成 UI 的业务层。

说真的，在 Vue 3 语境下，我越来越觉得组件设计的核心不是抽象能力，而是画边界的能力。组件是一个协议实体，它通过 props 接收输入，通过 emits 报告事件，通过 slots 给出扩展点。你能把这三条线画清楚，组件就能活得久。画不清楚，再通用也是给自己挖坑。

这篇文章我不打算聊怎么写按钮。我想聊的是，当你在做中大型项目的组件设计时，哪些边界一定要守死，哪些扩展点一定要克制，以及哪些看起来聪明的做法其实是在透支未来。

## 把组件当作协议，不是 UI 片段

你把组件当协议来看待的时候，有四个问题必须回答。

组件输入是什么，哪些 props 是必需的，哪些是可选的，哪些之间是互斥关系。组件输出是什么，会触发哪些事件，payload 的结构长什么样。组件的扩展点在哪里，哪些位置允许通过 slot 替换，替换的时候能拿到什么上下文。第四个问题最容易被忽略，你的组件不负责什么，哪些行为应该交给上层业务或者页面编排层。

我自己的感受是，缺少第四条的组件迟早会变成隐形业务层。表面上它是 UI，实际上它在决定流程走向、权限校验、缓存策略这些高层规则。短期能用，但等到你想重构的时候就会发现，这个东西已经跟业务长在一起了，根本扯不开。

## 状态归属：谁拥有状态，谁就承担一致性责任

组件设计里最要命的边界是状态归属。你得想清楚，状态到底是父组件控制的，还是组件自己持有的，又或者两者都支持但得有个明确的优先级。

Vue 3 里的 v-model，也就是 modelValue 加 update:modelValue，是最常见的受控模式。重点不在于语法怎么写，而在于一致性责任。父组件拥有状态，就得负责状态的合法性、持久化和跨模块同步。子组件负责展示和交互，不应该偷偷改那个唯一真相。

一个工程上比较稳的写法是同时支持受控和默认值，但规则要明确。优先用 modelValue，没有就用内部状态。任何变更都通过 emit 往上报，绝对不在内部悄悄改了不吱声。

```ts
type Props = {
  modelValue?: string
  defaultValue?: string
  disabled?: boolean
}

type Emits = {
  (e: 'update:modelValue', v: string): void
  (e: 'change', v: string): void
}

const props = withDefaults(defineProps<Props>(), {
  defaultValue: '',
  disabled: false
})
const emit = defineEmits<Emits>()

const inner = ref(props.defaultValue)
const value = computed(() => props.modelValue ?? inner.value)

function setValue(v: string) {
  if (props.modelValue === undefined) inner.value = v
  emit('update:modelValue', v)
  emit('change', v)
}
```

这段代码的边界画得很清楚。组件永远不直接写父组件的状态，只发事件。父组件要不要接管状态，是显式选择的结果，不是隐式约定。

## 扩展点策略：slot 不是万能定制接口

slot 确实很强，但它也是最容易把边界打穿的扩展机制。一个很典型的场景是这样的，组件一开始只有一两个 slot，后来某个业务场景需要定制，就加一个 slot，再后来又一个场景需要，再加一个。最后组件变成了一个模板容器，里面的逻辑还在承担各种复杂职责，结构跟逻辑互相绑架，谁都动不了。

我对 slot 有三个约束原则。

slot 应该服务于结构扩展，不应该作为数据流的主要通道。slot 的上下文数据，也就是 slot props，必须稳定、可文档化，而且尽量少。当你发现 slot 需要把大量内部状态暴露给外部的时候，大概率不是 slot 不够用，而是组件边界画错了，应该拆分职责而不是继续加 slot。

工程上更靠谱的做法是这样的，把可替换的结构做成 slot，把可配置的行为做成 props，把行为变化做成 emits。让协议的三个面各管各的，不要串。

还有一点经常被忽略，slot 也应该有契约。没有契约的 slot 会变成什么都能往里塞，最后你的组件不得不为外部传入结构的副作用负责，布局被破坏了、交互不可用了、可访问性退化了，全是你的锅。在 Vue 3 的工程实践里，建议把 slot 的可用上下文写成显式类型，让使用方知道能拿到什么、不能依赖什么。

```ts
type Slots = {
  // 允许替换标题区域，但只暴露最小上下文：title 文本与一个关闭动作
  header?: (p: { title: string; close: () => void }) => any
  // 列表项结构扩展：只给出 item 与 index，不暴露内部状态机
  item?: (p: { item: { id: string; name: string }; index: number }) => any
  empty?: () => any
}

defineSlots<Slots>()
```

## 组合与组件：composable 负责能力，组件负责协议

Vue 3 的 composable 确实容易让人上头。逻辑抽象突然变简单了，于是有人开始把组件做得很薄，把所有东西塞进 composable，组件最后就剩一个模板和几行胶水代码。

这个方向本身没有错，但必须画一条线，composable 负责能力，组件负责协议。

能力是可组合的状态机和副作用策略。协议是对外的契约。一个健康的结构通常是这样的。

composable 里不依赖具体 UI，不 import 组件，不依赖 DOM 结构。composable 暴露的是动作加派生状态，而不是随意可写的内部状态。组件在顶层声明 props、emits、slots，然后把这些映射到 composable 的输入输出。

当你把协议层和能力层分开之后，你会获得一个很稳的重构路径。协议不变的时候可以放心重写能力实现，能力复用的时候可以基于它产出多个不同协议的组件。两个方向都通，这才叫解耦。

## 失败语义与降级：组件要声明失败时会发生什么

可维护性很大一部分来自失败语义是否清晰。请求失败了怎么办，校验不通过怎么办，外部依赖缺失了怎么办。

如果组件把失败吞掉，只 console.error 一下或者静默不显示，问题会在上层以更难定位的方式暴露出来。如果组件把失败放大，直接 throw 或者弹一个强耦合的提示框，那它又把业务规则绑死在了组件内部，换个场景就用不了。

我更推荐的方式是把失败当作协议的一部分。用 emits 把失败和重试意图抛给上层，由上层决定展示策略和兜底方式。组件内部只做最小默认展示和可恢复动作，不擅自决定应该怎么提示用户。

```ts
type Emits = {
  (e: 'error', payload: { code: string; message: string; cause?: unknown }): void
  (e: 'retry'): void
}

const emit = defineEmits<Emits>()

async function load() {
  try {
    // ... fetch
  } catch (cause) {
    emit('error', { code: 'LOAD_FAILED', message: '加载失败', cause })
  }
}

function retry() {
  emit('retry')
  void load()
}
```

## 组件的不可变部分：把不变量写进类型与约束

组件可维护性的一个重要来源是不变量明确。

比如某个表单控件必须有 name 或 id 才能被可访问性工具识别。比如某个列表必须保证 key 稳定，否则更新的时候会抖。比如某个异步操作必须具备取消语义，否则竞态条件会回写旧值。

这些不变量如果只写在注释里，时间一长就会被遗忘。如果你能把它们部分写进类型、写进运行时校验、写进默认行为，维护成本会显著降低。

在 Vue 3 里你至少可以做到这些。用 props 类型表达互斥和必需关系，用 emits 签名表达事件 payload 的结构。不要让组件能不能用对这件事只能靠 code review 来保障，那样成本太高了。

## 复杂度预算：组件不是越通用越好，而是越可预测越好

通用性的代价往往是分支爆炸。你可以把组件的复杂度看成一个预算。

每加一个 prop 或 slot，都会增加组合空间。组合空间一大，测试成本和理解成本就不是线性上升了，而是指数级的。当复杂度超过某个阈值，组件会从可复用资产变成不可触碰遗产。

所以更合理的策略是分层通用。

基础组件，协议稳定，组合空间可控，几乎不包含业务语义。领域组件，承载领域语义，但扩展点更少，面向固定的业务域。页面编排层，把变化最快的逻辑留在这里，用组合的方式把领域组件拼起来。

说真的，很多团队翻车都翻在把第二层写成了第一层。把领域语义塞进基础组件，最后基础组件被业务绑架，谁都动不了。

## 常见误区与反模式：可复用变成不可维护的路径

聊了这么多原则，最后说说我在实际项目里反复见到的几种翻车姿势。

第一种，组件内部直接访问全局 store、router 或者 api。短期少写了几个 prop，长期任何重构都会牵一发动全身。这种耦合是最隐蔽的，因为代码能跑，review 的时候也不一定觉得有问题。

第二种，为了兼容所有场景不断加 boolean prop。showX、enableY、useZ，一个接一个。这会制造大量隐式组合，最后谁都不确定某个组合到底有没有被测过。

第三种，滥用 slot，把内部状态和行为通过 slot props 大量暴露给外部。你以为给了外部更大的灵活性，实际上外部开始依赖你的内部实现细节了。你改一下内部逻辑，外面全炸。

第四种，把组件当作业务规则容器。权限判断在里面做，流程跳转在里面做，缓存策略也在里面做。组件应该表达 UI 协议，规则应该在上层编排，这个分界不能模糊。

第五种，认为写成 composable 就等于解耦了。composable 也可能是耦合放大器，关键在于它是否依赖了具体上下文，是否暴露了可维护的不变量。不是用了 composable 就万事大吉，它跟组件一样需要边界意识。

## 边界感决定组件寿命，协议清晰决定团队速度

聊到最后，我想说的其实就一件事。Vue 3 组件设计最重要的不是你抽象能力有多强，而是你能控制住抽象的半径。

组件越通用、扩展点越多、内部规则越复杂，就越需要你用协议把边界钉死。钉不住，就不要硬做通用。宁可写两个略显重复的组件，也不要写一个谁都不敢动的万能组件。

状态归属必须明确，避免双写和幽灵状态。扩展点要克制，slot 服务于结构而不是承载数据流。能力与协议分离，用 composable 承载能力，用组件承载契约。

这三条守住了，组件库不会变成隐形业务层。团队也不会在改一个组件影响十个页面的恐惧里慢慢消耗速度。
