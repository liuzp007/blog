我前阵子帮一个朋友排查一个性能问题，他的页面列表拖一下就卡成幻灯片。他跟我说他已经把能优化的全优化了，computed 加了，shallowRef 换了，v-memo 也上了，甚至把几个组件都做了 markRaw。

结果性能还是一塌糊涂。

我打开 DevTools 的 Performance 面板一看，同一个组件在一个 tick 里被调度了七次。不是渲染慢，是渲染了太多次。坦率的讲，这种情况我见过太多了。很多人做 Vue 3 性能优化的第一反应是到处加缓存，好像 computed 和 memo 是什么万能药，往上一贴就好了。

说真的，这些 API 当然有用。但如果你把它们当成提速按钮，最终会陷入两种局面。要么你加了一堆优化点，代码复杂度肉眼可见地上升，性能却没有本质改善。要么你偶尔提速了，但业务继续增长之后性能又退化，而且你很难解释为什么会退化。

原因其实挺简单的。Vue 3 的核心性能优势不是某个 API，而是它用依赖关系加调度队列来管理更新。你要优化，就应该从依赖关系是否真实、更新是否可合并、作业是否可去重这些角度入手，而不是从哪里可以缓存入手。

这篇文章我试着给你一个工程可用的解释框架。当页面卡顿的时候，你应该先问哪些问题，看哪些信号，修改哪些结构。以及为什么这些修改在 Vue 3 的调度模型里能稳定产生收益。

## 渲染不是「执行 render」，而是「执行一个带调度语义的 effect」

这句话听起来有点绕，我换个说法你可能更容易理解。

在 Vue 3 里，组件渲染可以视为一个响应式 effect。它会读取响应式状态，然后形成一个依赖集合。当依赖变化的时候，它不会立刻同步重渲染，而是进入调度队列排队。

这有什么重要的呢。重要的地方在于，你在组件内写的每一次响应式读取，都可能成为未来触发更新的原因。

也就是说，性能问题的根源其实是依赖关系问题。

我自己的感受是，依赖关系出问题一般有三种情况。

第一种是依赖过多。一个渲染 effect 订阅了太多状态，结果任何细小的变化都触发大范围更新。就像你微信加了五千个好友，任何一个发朋友圈你都能看到，信息量直接爆炸。

第二种是依赖不稳定。每次渲染读取的依赖集合变化很大，比如分支读取或者动态 key，导致触发行为完全不可预测。有时候变一下居然不更新，有时候没变居然更新了，搞得你怀疑人生。

第三种是依赖失真。渲染依赖了一些本不该影响 UI 的状态，比如统计数据、缓存中间态、临时计算结果。这些状态在变，但 UI 不应该因为它们而变。

如果你只在更新很频繁这个层面做优化，往往会错过根因。更新频繁是结果，依赖建模才是原因。

## job queue 把更新当成作业，收益来自去重与合并

说到调度这块，Vue 3 的调度器可以概括为两步。

第一步是 trigger 产生意图，告诉系统这个 effect 需要重新跑。第二步是调度器把 effect 包装成 job 放入队列，做去重，然后在合适的时机 flush。

你可以用下面的伪代码理解核心语义。这依然是心智模型，不是源码。

```ts
type Job = () => void
const queue: Job[] = []
const queued = new Set<Job>()
let flushing = false

function queueJob(job: Job) {
  if (queued.has(job)) return
  queued.add(job)
  queue.push(job)
  if (!flushing) {
    flushing = true
    Promise.resolve().then(flushJobs)
  }
}

function flushJobs() {
  try {
    for (const job of queue) job()
  } finally {
    queue.length = 0
    queued.clear()
    flushing = false
  }
}
```

你看这段代码里的 queued 是个 Set，同一个 job 放进去两次会被自动去重。这就是为什么同一个组件在一个 tick 内被多个依赖触发多次，最终只会渲染一次。

工程意义非常直接。

去重让同一个组件免于重复渲染。合并让多次状态变更合并成一次渲染，避免中间态带来的无意义重算和 DOM patch。顺序保证父子组件更新、watch 回调、post-flush 任务按语义执行。

当你理解了这些收益来源，你就知道该怎么优化了。让 job 更少、更稳定、更可合并。而不是让某个更新更快执行。加快一个本不该执行的更新是没有意义的。

## flush 语义：性能问题经常是时序语义错误伪装出来的

在业务代码里经常出现一种现象。你为了让 UI 及时更新，在 watch 里写了大量同步逻辑，或者在事件处理里连续 set 多个状态，然后为了修正时序再加 nextTick。

这类代码的典型问题是你在和调度器对抗。

怎么说呢，Vue 3 的 flush 语义宏观上可以理解为三类。

pre 是 DOM 更新前执行，适合做准备工作或者同步派生，但要谨慎，容易影响渲染链路。render 是组件渲染与 patch，这是核心链路。post 是 DOM 更新后执行，适合读取布局、聚焦、启动动画这些操作。

当你把应该 post 执行的逻辑放进 pre 或者同步执行，就会出现两种后果。

性能上，你把本可延后的工作挤进了关键路径，帧时间被拉长了。正确性上，你读取了还没更新的 DOM 或者旧的布局，然后被迫写补丁式修复，更多 nextTick，进一步恶化性能。

所以很多性能问题的第一修复不是减少计算，而是把工作移出关键路径。

这也是为什么我说调度语义是性能治理的一部分。不是你代码写得不够快，是你把代码放错了地方。

## 依赖关系才是渲染范围的决定因素

如果你把 Vue 3 的更新理解为状态变了组件就更新，你在优化上会很被动。更准确的表达是，依赖变了，订阅了该依赖的 effect 会被调度。

所以渲染范围不是由组件层级决定的，而是由依赖图决定的。

这带来一个很实用的工程策略。把高频变化的状态与大面积渲染解耦。

怎么解耦呢。把高频状态放在更小的组件或者更小的 effect 范围里，比如拆分子组件、拆分渲染区域。把高频状态从深层 reactive 换成 shallowRef，避免深层属性读取形成大量依赖。把不需要响应式的对象用 markRaw 或者普通对象隔离，避免被 track。

我想强调的是，这些手段的本质都是改变依赖图，而不是让某个点的计算变快。

这也是我朋友那个问题的根因。他的依赖图太大了，一个列表项的状态变化触发了整个列表的重渲染。加多少 computed 和 memo 都没用，因为问题不在计算成本，而在触发范围。

## computed 与派生，把昂贵计算从热路径挪到冷路径

在 Vue 3 里 computed 的意义不只是缓存。说真的，如果只是缓存的话，手写一个变量存一下也行，何必用 computed。

computed 真正厉害的地方在于它把派生计算变成了按需求值。当依赖变化的时候，computed 通常只标记 dirty，而不是立刻重算。重算发生在真正读取它的时候。

这对性能优化的启示是，你要把昂贵计算尽量表达为 computed，并让它的读取点尽量靠近真实消费点。不要在很多无关的地方提前读取它，否则 dirty 标记了就得在那里触发更新。

同时要小心一个隐蔽的坑。

computed 返回的值如果是新引用，比如新对象或者新数组，即便内容相同，也会导致下游依赖认为它变化了，从而触发额外更新。

解决方案不是禁用 computed，而是返回稳定引用。复用对象、复用数组，或者拆分为多个原子 computed。同时降低下游订阅面，让下游只订阅它真正需要的字段。

这块需要注意一下，我之前在一个项目里就踩过这个坑。一个 computed 返回了 filter 之后的新数组，结果每次 filter 都是新引用，下游组件不管内容变没变都重新渲染了。找这个问题找了半天，最后发现是引用稳定性的事。

## watch 让副作用有边界，否则你在制造额外 job

watch 的正确定位是副作用边界。

什么意思呢。你用 watch 做派生的时候，相当于自己在维护一个调度系统。什么时候运行、运行顺序、去重、竞态、取消，全都得你自己处理。结果就是你引入了额外 job，而且这些 job 可能挤进关键路径。

更工程化的做法是这样的。

派生用 computed，把依赖传播交给响应式系统。副作用用 watch，并把 flush 放在语义合适的位置，比如读布局放 post。异步副作用要有取消语义，避免旧请求回写造成额外渲染与状态抖动。

下面是一个更接近工程现实的副作用写法，示意一下。

```ts
import { ref, watch } from 'vue'

const q = ref('')
const data = ref<any[]>([])
const loading = ref(false)
const error = ref<string | null>(null)

watch(
  q,
  async (next, _, onCleanup) => {
    let cancelled = false
    onCleanup(() => {
      cancelled = true
    })

    loading.value = True
    error.value = null
    try {
      const res = await fetchData(next)
      if (cancelled) return
      data.value = res
    } catch (e: any) {
      if (cancelled) return
      error.value = String(e?.message || e)
    } finally {
      if (!cancelled) loading.value = false
    }
  },
  { flush: 'post' }
)
```

这里的关键不是 fetchData 怎么写，而是取消语义。没有取消的话，旧请求回写会引发无意义的更新。而且这种更新往往最难定位，因为它不是频繁输入导致频繁请求那么直观。

你可能觉得取消逻辑写起来啰嗦，但它省下来的调试时间远超你写它的那几分钟。

## 性能优化的正确问题不是哪里慢，而是为什么会触发

当你观察到渲染频繁的时候，你应该优先问四个问题。

触发源是什么依赖？是哪个响应式 key 触发的？

依赖范围为什么这么大？为什么这个渲染 effect 会订阅它？

触发是否可合并？是否存在同 tick 多次触发同 job 的情况？

触发是否必要？这个变化是否真的需要影响 UI？

这四个问题全部指向依赖关系与调度，而不是指向某段代码执行慢。

我有时候觉得，很多性能问题的本质不是你写了慢的代码，而是你做了太多次正确但不必要的计算。单次计算再快，乘以一千次也是灾难。

## 常见误区与反模式

顺手聊几个我经常看到的误区和反模式。

第一个是同步写很多状态然后中途读 DOM。你在一次用户交互里同步写了一堆状态，写着写着又去读 DOM 和布局，结果强制同步测量，还搞出多次 flush。正确做法是把 DOM 读取放到 post-flush。

第二个是把大量派生逻辑写在 watchEffect 里。依赖集合随分支变化，更新范围时大时小，性能波动明显而且难以复现。在线上偶尔卡一下，本地怎么都复现不出来，就是这种问题。

第三个是 computed 返回新对象或新数组作为 props 传递。下游组件即便内容不变也被认为变了，触发额外渲染。这跟上面说的引用稳定性是一回事。

第四个是遇到卡顿就到处加 memo 和 cache。缓存只能降低单次执行成本，但更常见的问题是执行次数过多。你应该先减少触发次数与订阅面，再考虑缓存。

第五个是把 nextTick 当成万能胶水。nextTick 修正的是时序，不会修正错误的依赖建模。滥用的话会把问题从可解释的依赖图变成不可解释的到处 await 之后才对。我见过最夸张的代码里一个函数里有五个 nextTick 嵌套，后来的同事看一眼直接放弃了。

## 依赖图治理，不是局部技巧堆叠

我一直觉得 Vue 3 性能优化最重要的能力是解释能力。

你能解释一个更新为什么发生、发生几次、在什么时机发生、能否合并、能否避免。能解释，才有稳定可复制的优化。不能解释，优化就会变成运气好像变快了。

所以我更推荐把性能工作当成依赖图治理来做。

先让依赖真实。渲染只依赖渲染必要的状态。那些统计用的、缓存用的中间态，该隔离就隔离。

再让依赖稳定。避免动态依赖漂移与无意义的新引用。computed 返回稳定引用，不要每次都 new 一个新对象出来。

最后让调度可合并。把非关键路径移出 render 链路，减少 job 数量与 flush 压力。

当你按这个顺序做的时候，Vue 3 的调度器就会成为你的盟友。反之，你会不断写出看似正确但其实在对抗调度器的代码，最终把系统复杂度与性能成本一起拉高。

回到开头那个朋友的问题。最后的修复方案不是加任何 API，而是把列表项的状态从父组件的 reactive 对象里拆出来，每个列表项自己管理自己的响应式状态。依赖图缩小了，触发范围收窄了，卡顿消失了。

有时候性能优化就是这么回事，不是代码写得不够花哨，是依赖关系没想清楚。

你的页面上有没有那种说不清为什么会重渲染的组件？也许该看看它的依赖图了。
