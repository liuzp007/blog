去年帮一个朋友排查一个线上 bug，他那个 Vue 2 项目里，子组件 emit 了一个事件名拼错了，父组件监听的是另一个名字，整整两个月没人发现。测试没覆盖到那个交互路径，code review 也没看出来，最后是用户反馈才兜住的。我当时就想，这种错误本不该拖到线上。

后来他们项目迁移到 Vue 3，用上了 script setup，类似的问题在 IDE 里直接就红了。不是因为他们写代码变仔细了，而是编译器替他们盯上了。这件事让我开始认真思考一个问题，同样是 TypeScript，同样是组件，同样是模板，为什么 Vue 2 时代很难做到的类型体验，Vue 3 做到了？

坦率的讲，答案不在"写法更现代"。真正发生的事情是，script setup 把组件的公共接口从"运行时对象加约定"升级成了"编译期可见的结构化信息"。编译器能看见你定义 props emits slots expose 的方式，然后它就能把这些信息投影到模板类型检查里，投影到组件使用方的类型提示里，甚至跟重构动作绑定在一起。

说真的，这才是质变的根因。不是语法糖，不是少写几行代码，而是信息流变干净了。

## 质变的根因：公共接口从"运行时约定"转为"编译期事实"

Options API 时代，组件接口通过 export default 一坨运行时对象来表达。TypeScript 能看到对象字面量，但它分不清哪些属性是给编译器消费的接口信息，哪些是运行时逻辑。时间一长你就会发现，props 的类型表达五花八门，有的用构造函数数组，有的用对象，有的用 PropType 泛型组合，推导路径复杂得要命，动不动就退化成 any。

emits 也一样，字符串数组和函数签名对象混着用，不同写法导致类型信息时有时无。更要命的是模板编译和 TS 类型检查之间没有强连接，模板里写错 prop 名或者拼错事件名，很多时候只能跑到线上才发现。

script setup 做的事情其实很单纯。组件的接口定义被放在顶层，以编译器宏的形式存在。我自己的感受是，宏的价值不在什么"魔法"，而在于它给编译器提供了稳定的 AST 锚点。编译器拿到这些锚点，就能以一致的形式产出信息，供类型工具链消费。

你可以这样理解，接口声明被移到了可被静态分析的区域，类型系统终于能持续地、低成本地参与接口治理了。

## defineProps：类型与默认值不再相互伤害

defineProps 的最佳用法不是"写得短"，而是把类型约束当作接口的一部分。你通常有两条路可以走，用 TS 类型参数表达 props 结构让类型系统做主来源，或者用运行时 props 选项表达校验与默认值让运行时做主来源。

在大型项目里最容易出问题的地方是，你既希望运行时有默认值和校验，又希望 TS 能精确推导。如果这两套东西分散在不同层，最终一定出现类型跟运行时不一致的情况。

更稳妥的策略是让类型做接口事实，默认值做实现细节，通过编译器提供的桥接能力把二者对齐。

```ts
import { computed } from 'vue'

type Props = {
  id: string
  pageSize?: number
  mode?: 'light' | 'dark'
}

const props = withDefaults(defineProps<Props>(), {
  pageSize: 20,
  mode: 'light'
})

const isDark = computed(() => props.mode === 'dark')
```

这里的关键不是 withDefaults 本身有多好用。关键是默认值和类型信息紧挨着，变更成本极低。你重构接口的时候不需要同时去改一堆分散在各处的对象选项和类型定义，在一个地方动就行了。

## defineEmits：事件是 API，不是字符串

我见过太多团队把事件当字符串随便抛。项目小的时候感觉不到什么，等项目一大，事件名冲突、事件参数不统一、调用方和实现方的契约漂移，这些坑会一个接一个往外蹦。

在 script setup 里 defineEmits 让你可以把事件当成带签名的 API。这件事非常关键。它把事件从"约定"变成了"可验证契约"，你可以强制规定每个事件携带的 payload 结构，让跨组件通信更接近函数调用而不是字符串拼接。

```ts
type Emits = {
  (e: 'update:modelValue', value: string): void
  (e: 'submit', payload: { id: string; silent?: boolean }): void
  (e: 'error', err: Error): void
}

const emit = defineEmits<Emits>()

function onSubmit() {
  emit('submit', { id: '42', silent: false })
}
```

说真的，这段代码在工程上最大的收益是可重构性。你改事件名或者 payload 字段，调用方在编译期就爆红了，而不是上线后在某个边角交互里悄悄失效。我朋友那个两个月没发现的 bug，用这种方式当天就能拦住。

## 模板类型检查：让模板成为工程系统的一部分

Vue 的模板不是 TypeScript 文件，但它可以被类型化。这是质变的第二个关键点。当编译器能把 template 里用到的变量映射回 script setup 的声明环境，模板就不再是黑箱了。

这会带来三个非常具体的变化。你在模板里写错变量名、写错 props 字段、写错事件名，IDE 直接报错。你在模板里对 ref computed props 的使用能获得正确的类型提示。你可以把组件 API 当作可搜索、可重构的符号，而不是一堆文本匹配。

我自己的感受是，这不应该被当作体验改良。这是质量机制。模板类型检查做的事情是把过去只能靠 code review 和测试兜底的错误，前移到编译期拦截。对于中大型团队来说这是成本结构的变化，你用更低的边际成本换来更稳定的接口一致性。

## defineExpose：把组件当成对象时请明确暴露面

任何框架都会遇到不得不越过声明式边界的时刻。比如你需要让父组件调用子组件的方法，聚焦输入框、滚动到某处、触发校验之类的。在 Vue 3 里 defineExpose 是一个很重要的治理点，它把实例可访问性从默认开放变成了显式声明。

坦率的讲，你应该把它当作最后的逃生门，而不是常规通信手段。因为它会把组件间依赖从数据流转成对象调用，这通常意味着更强的耦合和更难的测试。

更好的使用方式有两点。只 expose 语义化动作，不 expose 内部状态。暴露的方法要稳定，避免暴露依赖内部实现细节的方法。

## 组件接口治理：props emits slots 是一套完整的协议

很多项目在定义组件时只认真对待 props，slots 和 emits 的契约就随意了。时间一长你会发现 props 是强类型的，slots 任意塞，emits 到处乱飞。组件系统逐渐失去一致性。

在 Vue 3 的工具链下你可以把三者当作组件协议的三条腿。props 描述输入，组件需要什么。emits 描述输出，组件能通知什么。slots 描述结构扩展，组件允许哪里被替换，替换时能拿到什么上下文数据。

一个工程化的目标是，当你查看一个组件时，能在顶层声明区看到完整协议，而不是在模板和逻辑里到处寻找隐含约束。这让组件更像模块而不是片段。

## 类型系统如何影响架构：把不变量写进签名而不是写进注释

在大型项目里真正昂贵的不是写代码，而是维护不变量。哪些值永远不为空，哪些状态不会同时出现，哪些事件必须按顺序触发。过去你可能用注释、文档、口头约定维护这些不变量，现在你可以把其中一部分写进类型签名，让工具链替你做持续校验。

比如一个列表组件的状态常见不变量是，loading 为 true 时不应该同时有 error，error 存在时数据可能是旧的但不应被当成新鲜数据使用。你可以用更精确的联合类型表达状态机，让调用方按规则处理。

说真的这不是类型洁癖。这是把系统复杂度从运行时排查转移到编译期约束。当团队规模增长，这种转移通常是净收益。

## 常见误区与反模式：类型体验变好之后更容易写出隐蔽耦合

我见过几个反复出现的坑。

第一个反模式是把所有东西都塞进 defineProps，然后在组件内部随意修改入参衍生状态。props 是输入，应该尽量保持只读语义，派生状态应由 computed 或内部 state 承担。

第二个反模式是为了省事把事件参数写成 any 或 unknown，最终把错误从模板前移又推回运行时。事件签名是跨组件契约，越是公共组件越不应该模糊。

第三个反模式是大量使用 defineExpose 进行跨层调用，形成组件实例依赖网。短期开发确实快，长期重构成本极高，因为你把依赖从数据流变成了对象图。

第四个误区是把 script setup 当作没有结构的自由区，所有逻辑平铺在顶层。写法自由不代表结构自由，你仍然需要按能力域拆分 composable，把组件文件控制在可理解范围。

第五个误区是把模板类型检查当成 IDE 小甜头。它是质量机制，不应被随意关闭或忽略，否则你会回到 Vue 2 时代那种模板错了靠测试兜的成本结构。

## script setup 的价值在接口可治理，不是代码更短

我更看重 script setup 带来的治理能力。它让组件接口变成编译期事实，进而让类型系统参与到接口的演进中。对团队来说，这带来两个好处，组件库可以更像产品，接口有版本感有契约有可验证的变更影响面。业务系统可以更像系统，能力抽象与组件协议更清晰，重构与迁移不再靠经验主义。

如果你的项目规模足够大，你会发现少写样板带来的收益很快耗尽。真正持续的收益来自让错误更早暴露，让接口更难漂移。

你现在的项目里，组件接口是由类型系统守护的，还是靠注释和约定撑着的？
