上个月接了个需求，给项目加一个新的设置页面。我心想这能有多难，打开编辑器就开干了。结果写完一回头，表单校验提示三四种风格，按钮间距跟其他页面对不上，loading 态有的地方转圈有的地方啥也没有。我自己都觉得这页面不像同一个项目出来的。

坦率的讲，这不是什么高深的设计问题，就是组件库用得太随意了。我们项目用的是 Ant Design v4，这玩意功能是真全，但你要是不给它套个规矩，十个人能写出十种风格来。

所以我就花了一个下午，把踩过的坑和摸索出来的约定整理了一份清单。不是什么权威规范，就是团队内部的一个最小可行约定，让大家新开页面的时候有个兜底。

## 全局配置与节律

说真的，AntD 最让人头疼的不是它不好用，是太好用了。你想改个圆角，`borderRadius` 一设就生效。想换个主题色，less 变量一覆盖就行。但问题是每个人都能改，改到最后全局 CSS 里全是覆盖补丁，像打了一层又一层的膏药。

我自己的感受是，全局配置这件事必须在一开始就定死。消息提示统一挂载到哪个节点，弹层的 z-index 怎么管，toasts 同时最多出现几条，这些全在入口文件里约束好。后面谁要是觉得某个场景需要例外，先来讨论，别闷头就覆盖。

```tsx
// src/config/antd_global.tsx（片段）
import { ConfigProvider } from 'antd'
export default (App: any) => () => (
  <ConfigProvider componentSize="middle">
    <App />
  </ConfigProvider>
)
```

组件尺寸我统一用的 middle。很多人可能觉得 small 能塞更多内容，但密密麻麻的表单真的很劝退用户。middle 是个比较好的平衡点，不会太拥挤也不会太浪费空间。

字体和圆角这些就不要在业务组件里随便动了，全部放在全局样式 token 里管。只有主题色这块，确实存在品牌定制的需求，但我会要求只在主题文件里覆盖，禁止在业务组件里直接写 `color` 值。

反正我觉得，节律这个东西，听着玄乎，其实就是一致性。用户在 A 页面看到的按钮间距是 16px，到 B 页面突然变成 12px，他自己可能说不上来哪里别扭，但就是觉得这产品不够专业。

## 表单与校验

表单这块踩的坑最多，我一个个说。

最早的时候我写表单校验，喜欢用自定义函数在 `onFinish` 里手动判断。后来发现这种方式有个致命问题，错误提示的展示位置不统一，有的在输入框下面，有的用 `message.error` 弹出来，还有的直接 `alert`。用户填一个表单，校验反馈像开盲盒。

后来统一用 `Form.Item` 的 `rules` 属性来声明校验规则。这玩意的好处是把校验逻辑和展示位置绑定在一起了，哪个字段有问题，提示就出现在哪个字段下面，用户一眼就知道该改哪里。

```tsx
// 表单片段
<Form layout="vertical" onFinish={onSubmit}>
  <Form.Item name="title" label="标题" rules={[{ required: true, message: '请输入标题' }]}>
    <Input maxLength={50} />
  </Form.Item>
</Form>
```

有一点我花了段时间才想明白。错误提示文字最好控制在一行，别写一长串。因为提示文字一换行，表单高度就变了，下面的内容会跟着往下挤，整个表单就开始抖。用户体验极差。我现在的习惯是提示文案控制在 10 个字以内，比如「请输入标题」「格式不正确」，简洁明了。

还有一个细节，提交失败后统一用 `message.error` 在顶部给一个全局提示，告诉用户具体哪里出了问题。别让用户自己去表单里找那个飘红的小字，挺费劲的。

## 列表信息密度

信息密度这件事，我之前走了两个极端。

第一个极端是恨不得一屏塞进去所有信息，卡片里塞满文字和标签，表格列排得密密麻麻。结果用户打开页面直接懵了，不知道该看哪里。

第二个极端是追求所谓极简设计，一个页面就放三张卡片，大量留白。看着是挺清爽，但用户为了找一个信息要滚三屏。

怎么说呢，合适的密度其实不难把握。我用卡片做内容分组，每个卡片承载一个明确的信息主题。表格和列表的操作列严格控制在 3 个以内，超过的折到「更多」下拉菜单里。这个数字没有科学依据，纯粹是体感，3 个以内的操作按钮视觉上还能分清主次，超过 3 个就容易眼花。

封面图和列表数据都做懒加载。坦率的讲，首屏加载体验太影响用户的第一印象了。卡片从空白突然弹出来那种闪烁感，真的很廉价。配合 Skeleton 骨架屏就好很多，用户至少知道这里会有内容，心理上有个预期。

```tsx
// 骨架占位
<Skeleton active loading={loading}>
  <YourList />
</Skeleton>
```

骨架屏的 `active` 属性建议加上，那个微妙的闪烁动画能给用户一种「正在加载」的感知，比纯灰色色块强太多了。

## 反馈与可达性

这块我一开始完全没当回事。觉得功能跑通就行了，反馈不反馈的无所谓。直到有一次我自己用测试账号走流程，点了个按钮啥反应没有，我愣了三秒才意识到已经操作成功了。那一刻我理解了为什么用户老是反馈「是不是卡了」。

所以我给自己定了个硬规矩，任何用户操作必须有反馈。保存成功给一个 `message.success`，删除操作弹个确认框，耗时任务上 `Spin` loading 或者全屏 Modal 遮罩。不能让用户去猜系统到底有没有在处理。

```tsx
// 统一消息提示
import { message } from 'antd'
message.config({ duration: 3, maxCount: 3 })
```

`maxCount` 设成 3 是有原因的。如果同时弹出太多消息提示，会互相遮挡，而且用户根本来不及阅读。3 条是个比较安全的上限。duration 设 3 秒也是体感值，1 秒太短读不完，5 秒又觉得它赖着不走。

可达性这块其实不太想展开说，因为我自己做得也不够好。但最低限度，所有可点击的元素要么有 `title` 属性，要么有可见的文字标签。保证键盘用户也能正常操作。这块投入产出比其实挺高的，改不了多少代码，但能覆盖到一批之前完全用不了你产品的用户。

## 收尾

我有时候觉得，Ant Design 这种组件库最大的价值不是它有多少组件，不是它有多好看。而是它给了一整套体验的可能性，然后你通过约定把这些可能性收敛到一条线上。

不需要多复杂的设计规范，也不需要专门的 UI 审查流程。就是几个简单可执行的约定，全局配置怎么管，表单校验怎么写，信息密度怎么控，操作反馈怎么做。把这些定下来，哪怕团队新来一个人，新开的页面也不会跟现有的风格差太远。

这份清单我自己也在持续更新，碰到新的坑就补一条。也许你用的技术栈不一样，但思路是一样的，在组件库给你自由度的地方，用约定把体验收口。
