# Vite 优化

## 动态导入

事情是这样的。

前两天我在做首页优化，打开 Chrome DevTools 一看那个 Network 面板，好家伙，首屏 JS bundle 直接干到 1.8MB。我当时就愣住了，这也太离谱了吧。

一个个人博客而已，怎么可能打出这么大的包。翻了翻代码才发现，所有的页面组件全部被静态 import 进来了，博客详情页、留言板、关于我、足迹地图，一大堆用户可能根本不会点进去的页面，全部在首屏就加载了。

坦率的讲，这个问题的根源其实挺好理解的。我们写代码的时候习惯性地把所有东西放到顶部 import，开发的时候确实方便，热更新也快，但生产环境下这就变成了首屏的噩梦。

Vite 给了一个特别好用的工具，就是 `import.meta.glob`。

```js
const pages = import.meta.glob('../pages/*/index.tsx')
```

这一行代码干的事情其实很简单，它把你的 import 变成了懒加载。只有在用户真正导航到某个页面的时候，对应的模块才会被请求和执行。

说真的，我自己的感受是，这个改动对性能的提升是立竿见影的。改完之后首屏 bundle 直接从 1.8MB 降到 400KB 左右，加载时间快了将近 3 秒。

你可能觉得 3 秒不算什么，但用户等 3 秒和等 0.5 秒的体验完全是两个世界。

这块需要注意一下，动态导入虽然好使，但也有坑。比如你在用 React Router 的话，需要配合 `React.lazy` 和 `Suspense` 一起用，不然组件异步加载的过程中页面会直接白屏，用户体验反而更差了。

还有一个小细节，`import.meta.glob` 默认是懒加载模式，如果你确实需要立即加载某些模块，可以加一个 `{ eager: true }` 的选项。但说实话，大多数情况下你不需要这个。

## 依赖优化

说完动态导入，顺着再聊聊依赖这块的事。

我之前有个很不好的习惯，什么东西都喜欢装个 npm 包。格式化日期要装 dayjs，深拷贝要装 lodash.deepclone，连一个简单的邮箱校验都要装 validator。时间一长，`node_modules` 比我的项目代码还大。

后来有一次做生产构建，看着那个打包分析图我才意识到问题的严重性。好多运行时依赖做的事情，其实在构建期就能搞定。

怎么说呢，其实吧，Vite/Rollup 的构建期能做的事情比我们想象的多得多。

比如你项目里有个常量配置文件，里面写了一堆条件判断和计算逻辑，但这些逻辑的输入在构建时就已经确定了。这种情况你完全可以把计算挪到构建脚本里去做，然后把结果直接写成一个 JSON 文件让运行时读取。

```js
// vite.config.mjs
import { defineConfig } from 'vite'

export default defineConfig({
  define: {
    __BUILD_TIME__: JSON.stringify(new Date().toISOString()),
    __COMMIT_HASH__: JSON.stringify(process.env.COMMIT_SHA || 'dev')
  }
})
```

就像上面这段代码，`define` 选项可以在构建时把变量直接内联替换掉，运行时连这个变量声明都不存在了，直接就是字面量。

我有时候觉得，前端工程化走到今天这一步，构建工具已经不再是一个简单的打包器了，它更像是一个预处理器。能提前干掉的活就不要留到运行时去干，用户的手机和浏览器会感谢你的。

还有一个比较骚的事，有些包你可以用更轻量的替代方案。比如 moment.js 当年多大一个包啊，整个时区数据库全塞进去了，结果大部分人其实只用到了格式化和解析这两个功能。换成 dayjs 之后体积直接缩了 90% 以上。我们项目里也做了这个替换，在 alias 配置里把 moment 指向 dayjs，几乎无痛迁移。

反正我觉得，依赖管理这件事不是说你不用第三方包，而是要在用之前多想一步，这个东西我真的需要在运行时引入吗，还是说构建期能提前处理好。

说到底，构建优化这件事没有什么银弹，就是一点一点把首屏不需要的东西挪走，把能提前算的东西提前算完，把多余的依赖砍掉。

听起来都是些不起眼的小事对吧，但就是这些小事加在一起，决定了用户打开你网站那一刻的体验。
