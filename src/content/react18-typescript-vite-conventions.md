事情是这样的。

前两天我在给博客加一个新页面，建好目录写完组件，刷新浏览器，页面自己就出来了。没改路由配置，没手动注册什么 map，甚至连 import 都没多写一行。那一刻我突然意识到，这个项目的约定体系已经跑通了一整圈，新加页面的心智负担基本降到了零。

我自己的感受是，一个项目能不能长期维护下去，看的不是用了多花哨的架构，而是每次加新功能的时候你能不能闭着眼睛都知道东西该放哪。坦率的讲，React 项目最怕的就是约定不统一，今天这个人在 pages 下建文件夹，明天那个人在 views 下搞组件，路由配置散落在五六个文件里，半年以后谁都不敢动。

所以今天想聊聊我们这套 React 18 + TypeScript + Vite 的约定体系，不是什么高深的东西，但确实是我们踩了不少坑之后留下来的一套比较舒服的实践。

## 页面与动态路由约定

先说页面这块。

所有页面组件统一放在 `src/pages/**/index.tsx`，目录名就是路由段，详情页通过参数或者查询串来承载。这个约定看着简单，但它解决了一个特别烦人的问题，就是路由配置的维护成本。你不用再去某个中央路由表里手动加一条记录，建好目录就完事了。

Vite 的 `import.meta.glob` 在这里面扮演了一个很关键的角色，它在构建期就能把所有页面组件发现出来，还顺带做了懒加载。

```ts
// src/router/autoPages.ts
export const modules = import.meta.glob('@/pages/**/index.{tsx,jsx}', { eager: false })
```

说真的，我之前用 Webpack 的时候也搞过类似的动态路由，那是用 `require.context`，写起来啰嗦，类型推断也不友好。Vite 这套方案简洁太多了，一个 glob 表达式把活干完，eager 设为 false 天然就是按需加载。

你可能觉得这没什么大不了的。但想想看，当项目里有四五十个页面的时候，每次加新页面不用动任何配置文件，这种感觉太爽了。

## 路径别名与统一导入

说到别名这块，这是我们很早就定下来的规矩。

以 `@` 指向 `src` 作为基础，然后又补充了 `@store`、`@router`、`@page` 这几个语义化的别名。这样做的好处是，你打开任何一个文件，导入路径一眼就能看出这个依赖来自哪一层，不用去脑补 `../../../` 到底指回了哪里。

```ts
// vite.config.js 片段
resolve: {
  alias: {
    '@': '/src',
    '@store': '/src/store',
    '@router': '/src/router',
    '@page': '/src/pages',
    'moment': 'dayjs'
  }
}
```

有个小细节你可能注意到了，我们还把 `moment` 别名到了 `dayjs`。这是因为项目早期用了 moment，后来迁移到 dayjs，为了兼容那些遗留代码就搞了个别名。这种做法我有时候觉得有点讨巧，但它确实让迁移过程丝滑了很多，不用一次性改几十个文件。

另外还有一条我们团队内部的规矩，导入顺序要保持 React → 三方库 → 本地模块 → 样式文件。这不是什么技术要求，纯粹是为了让 git diff 更干净，改一个 import 不会把整个文件的重排都带出来。

我觉得还是挺重要的。

## RTK 作为首选状态层

坦率的讲，状态管理这块我们折腾过不少方案。

最早用的是老的 Redux +\_OBS 那一套，boilerplate 多到让人怀疑人生。后来团队统一决定，新模块一律走 RTK，全部收敛到 `src/store/` 下面，用 slice 来组织状态和异步逻辑。

```ts
// src/store/index.ts
import { configureStore } from '@reduxjs/toolkit'
import ui from './slices/ui'
export const store = configureStore({ reducer: { ui } })
export type RootState = ReturnType<typeof store.getState>
```

RTK 的 slice 写法让状态和 reducer 待在一起，你不用再在五个文件之间跳来跳去才能看懂一个状态流转。对于一个持续迭代的项目来说，这种局部内聚的设计对维护效率的提升是实打实的。

反正我觉得，选状态管理方案不用纠结什么"最佳实践"，能让大家写起来舒服、改起来不慌就是好方案。RTK 对我们来说就是那个恰到好处的选择。

## 代码片段渲染规范

这个可能偏我们博客项目自己的需求了，但我觉得思路可以分享。

教程类文章里的代码块，我们用字符串代码块来显示，不搞什么沙箱运行。如果某个示例真的需要交互，就放进 `src/examples/` 下面做懒加载。高亮和复制按钮这些通用功能，全部交给 `CodeBlock` 和 `BeautifyCode` 组件统一处理。

```tsx
// 片段：在文章中嵌入代码块的最小示例
export default function Hello() {
  return <div>Hello</div>
}
```

这样做的好处是文章内容保持纯文本的可维护性，交互能力又不会缺失。说实话我也不确定这是不是最优解，但至少跑下来效果不错，文章编辑和代码复用都挺方便。

说到底，页面发现、路径别名、状态管理这三件套定下来之后，新增页面和模块就变成了一件很机械的事情。建目录，写组件，导 slice，完事。系统能自动识别你。

我一直觉得好的约定就是那种你感受不到它存在的约定。你只管写业务代码，框架在背后默默帮你把路由注册了，把状态挂上了，把路径解析对了。

你项目里的约定体系是什么样的？有没有什么踩过坑之后才想明白的规矩？
