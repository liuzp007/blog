事情是这样的。

去年有个朋友找我喝酒，说他带队搞 Vue 2 到 Vue 3 的迁移，搞了三个月，版本号确实换成 3 了，但团队开发效率比迁移前还低。新来的同学看代码一头雾水，老同学也不敢随便改东西了。他问我，是不是哪一步走错了。

我看了他们的代码，坦率的讲，这根本不是哪一步走错的问题，而是从一开始就跑偏了。

他们把 80% 的时间花在了 setup()、ref()、reactive()、defineComponent() 这些语法细节上，线上回归、协作效率、组件抽象质量这些真正影响工程成本的东西，反而没人管。最后就是版本号换了，复杂度一点没变，甚至更乱了。

说真的，我一直觉得 Vue 2 到 Vue 3 的迁移，根本不是语法迁移，而是心智迁移。

你得把「我在组件里写逻辑」的习惯，变成「我在系统里建边界」的习惯。把「框架替我处理很多隐式的事情」的舒适区，变成「依赖是显式的、生命周期是显式的、抽象是可组合的」这种更工程化的表达方式。

如果你的迁移目标只是「能跑起来」，你会得到一个能跑但越来越难治理的 Vue 3 项目。如果你的目标是「把系统复杂度降回可控」，你才会知道该留什么、该换什么、该推迟什么，以及什么时候该停下来补齐能力，而不是盲目搬代码。

我自己也不确定下面这条路线是不是最优的，但至少它是风险可控、增量可验证、成本能解释清楚的。同时我会把一些常见的坑直接点出来，帮你避免把迁移做成一场组织性事故。

## 先定义「迁移完成」的标准，不是版本号，而是成本曲线

怎么说呢，你用什么标准定义「迁移完成」，直接决定了你的路线。

只看版本号，你就会为了尽快升上 Vue 3 做各种折衷。只看功能上线，迁移就会变成永远在背景里嗡嗡响的噪音，永远推不完。

更合理的方式是定义一组可以被验证的目标，覆盖四类成本。

交付成本，就是迭代速度、回归周期、线上发布失败率这些。维护成本，代码阅读成本、组件复用成本、依赖升级成本。质量成本，缺陷密度、线上问题定位时长、可观测性，日志、错误边界、回滚路径。组织成本，新同学上手时长、团队对「正确写法」的一致性、评审争议密度。

你不用把这些都量化得很精确，但至少得有个能对齐的口径。比如「迁移完成」不是页面都换成 Vue 3 了，而是核心业务链路在 Vue 3 下跑得稳，e2e 用例稳定通过，而且新功能只在 Vue 3 侧开发。再比如「迁移完成」不是 Options API 都改成 Composition API 了，而是复杂模块的抽象方式统一了，不再依赖隐式 mixin 和全局副作用，逻辑复用以 composable 为主。

当你把迁移当作成本曲线优化来看，有两个关键决策自然就清楚了。哪些东西可以用兼容层过渡，哪些必须重做。哪些回归风险必须前置验证，哪些可以后置清理。

## 心智迁移 1，从 defineProperty 到 Proxy，不是能力变强，而是语义更清晰

聊到 Vue 2 的响应式，我自己也踩过不少坑。

那时候写起来确实爽，框架把很多约束藏在里面了，对象的属性通过 getter/setter 收集依赖，数组方法被 patch 过，渲染更新通过 watcher 队列批处理。代价就是你得记住一批「坑位」，新增属性需要 Vue.set，数组下标赋值不触发响应，某些深层对象的变更追踪不直观。

Vue 3 通过 Proxy 把「能不能追踪」从靠补丁变成了语义上的统一。访问就 track，变更就 trigger。很多人看到这里就得出结论，Vue 3 更强了，迁移就是把 API 替换掉。这话听着没错，但注意力放错地方了。

更重要的变化是，你开始被迫把「数据形态」和「依赖边界」当作工程设计对象来看待。

在 Vue 2 时代，你可能习惯在任意地方把一坨对象塞进 data，然后在各个组件里随意读写。到了 Vue 3 时代，这种做法会让依赖关系变得更隐蔽更难治理，因为一切都能被追踪，一切也都可能触发更新。

迁移时你要问的不是这个对象 reactive 之后会不会更新，而是这个状态应该被谁拥有？是组件、composable、store 还是服务层？哪些字段属于领域状态，哪些只是 UI 状态？别把 UI 细节扩散到共享状态里去。依赖集合是不是稳定的？别让 render 依赖随条件分支频繁变动造成抖动。

一个典型的迁移点是「把 Vue 2 的 data 巨对象拆开」。在 Vue 3 里，你更应该把状态按职责拆成多个更窄的响应式来源，而不是让一个巨大的 reactive 对象承担所有语义。

```ts
// Vue 3 里更可治理的做法：按职责拆分状态来源
import { reactive, ref, computed } from 'vue'

const query = reactive({ keyword: '', page: 1, pageSize: 20 })
const ui = reactive({ loading: false, error: '' })
const items = ref<Array<{ id: string; title: string }>>([])

const hasMore = computed(() => items.value.length < query.page * query.pageSize)
```

这不是写法升级，是边界升级。你在把「会一起变化的东西」放一起，把「不同生命周期的东西」拆开，降低更新耦合。

## 心智迁移 2，从 mixin 到 composable，变化的是抽象单位与依赖表达

说到 mixin 这块，我有时候觉得它是 Vue 2 大型项目里最让人头疼的东西之一。

不是说它功能不够，而是它把依赖变成了隐式的。你在组件里看不到 mixin 注入了什么数据、方法、生命周期。多个 mixin 叠加时更糟，命名冲突、时序冲突，最后只有少数人敢动那段代码。

Vue 3 的 Composition API 让逻辑复用回到了更接近「普通函数」的形态。composable 是显式调用的，依赖可以通过参数显式传入，返回值是明确的能力集合。

但迁移的难点不在于把 mixin 改成函数。而在于你必须重新定义抽象的边界。

你这个 composable 要解决哪一类问题？领域能力、UI 交互、数据访问还是副作用编排？输入输出是什么？输入越多越像工具函数，输出越多越像小型框架。生命周期怎么管理？watch 和 watchEffect 的 cleanup 由谁负责，副作用能不能被测试？

如果你只是把 mixin 的内容原封不动搬进一个 useXxx() 函数，再在组件里调用，你大概率会得到更难读的代码。因为你同时失去了 Options API 的结构化约束，data/methods/computed 那种清晰分区，也没有建立新的抽象约束，输入输出和依赖方向都没有。

迁移的正确姿势是，先把 mixin 里隐藏的依赖显式化，再决定它应该变成 composable 还是 store 模块，还是干脆应该回到组件内部。

```ts
// 反例：把 mixin 直接搬进 composable，依赖仍然隐式
export function useBadThing() {
  // 这里偷偷读了全局 store、路由、以及 window 状态
  // 组件看不到依赖，测试也难做
}

// 更可控：把依赖显式参数化
export function useSearch(params: {
  fetcher: (q: string) => Promise<string[]>
  debounceMs?: number
}) {
  // ...
}
```

这里的核心不是函数更优雅，而是依赖可见。当依赖可见，评审和排障的成本会显著下降。

## 心智迁移 3，从「生命周期钩子堆叠」到「副作用编排」，学会管理 cleanup

顺着上面的再聊聊副作用管理。

Vue 2 的生命周期钩子让人容易把逻辑写散，mounted 里绑事件，watch 里触发请求，beforeDestroy 里清理，跨多个 mixin 后更是难以追踪。Vue 3 的 onMounted、onUnmounted、watch、watchEffect 并不会自动帮你变好，它只是提供了更好的编排能力。

迁移时最容易出问题的是 cleanup。

事件监听、定时器、订阅如果不清理，会造成泄漏或重复执行。watch 的依赖如果过宽，会造成不必要的副作用触发，甚至引入竞态条件。watchEffect 的自动依赖收集如果没有边界，会把不该成为依赖的东西也绑进来。

在 Vue 3 里我更推荐把副作用写成「可取消的任务」，并把取消逻辑与触发逻辑放在同一个作用域内。这样在迁移时更容易验证行为一致。

```ts
import { ref, watch, onUnmounted } from 'vue'

export function useCancelableRequest<T>(run: (signal: AbortSignal) => Promise<T>) {
  const data = ref<T | null>(null)
  const error = ref('')
  const loading = ref(false)

  let ctrl: AbortController | null = null
  const exec = async () => {
    ctrl?.abort()
    ctrl = new AbortController()
    loading.value = true
    error.value = ''
    try {
      data.value = await run(ctrl.signal)
    } catch (e: any) {
      if (e?.name !== 'AbortError') error.value = String(e?.message || e)
    } finally {
      loading.value = false
    }
  }

  onUnmounted(() => ctrl?.abort())
  return { data, error, loading, exec }
}
```

这类抽象在 Vue 2 里也能做，但 Vue 3 的组合式写法更自然。迁移的重点是，把「副作用散落在各处」收敛成「有边界、可取消、可复用」的能力。

## 生态迁移，你以为在迁框架，其实在迁「依赖图」

回到迁移这块，Vue 2 项目迁移的真实阻力，往往不是框架本身，而是生态。

路由、状态管理、UI 组件库是否支持 Vue 3。自研插件，prototype 注入、全局指令、全局 filter，能不能平滑迁移。构建工具链和代码规范是不是需要同步调整。

很多团队犯的错误是把生态迁移当作「顺手改掉」。框架升级过程中顺便换路由，顺便换 store，顺便换构建工具，顺便换 UI 库。最后任何一个回归都无法定位原因，因为你同时更换了太多变量。

比较骚的事，很多团队觉得自己是在高效推进，其实是在叠加风险。

更可控的方式是明确迁移顺序。先稳定住「应用运行的基本壳」，再逐步替换内部能力。比如先把全局注入从 Vue.prototype 迁到 app.config.globalProperties，同时建好类型约束。再把全局 filter 替换为显式函数或 computed，避免模板里出现隐式依赖。最后再处理 UI 组件库与指令的迁移，这类回归可视化强，适合做 e2e。

```ts
// Vue 2:
// Vue.prototype.$http = httpClient

// Vue 3:
import { createApp } from 'vue'
import App from './App.vue'
import httpClient from './httpClient'

const app = createApp(App)
app.config.globalProperties.$http = httpClient
app.mount('#app')
```

这段代码的重点不在写法换了，而在「全局依赖是否可追踪」。你可以逐步收敛 $http 的使用范围，甚至未来替换为显式注入或者服务层。

## 回归策略，把迁移当作「行为合同」验证，而不是「UI 对齐」

迁移最可怕的不是显性的报错，而是隐性的行为偏移。

某个 watch 触发时机变了，某个 computed 的依赖集合变了，某个组件更新被更频繁地触发，最终表现为「偶现 bug」「线上卡顿」「部分用户复现不了」。这种东西排查起来真的让人崩溃。

所以迁移时最重要的工程动作之一，是建立「行为合同」。

关键链路的输入输出合同，在同样输入下，输出结构、错误码、加载状态是否一致。关键交互的时序合同，点击然后 loading 然后成功或失败然后 UI 状态，是否遵循既定时序。关键缓存的失效合同，路由切换、筛选条件变化时，缓存是否正确失效。

这类合同最好用自动化覆盖，而不是靠人工点点点。你不需要一下子把覆盖率做得很高，但要让它足够「抓住大事故」。实践上我更建议对核心链路做 e2e，最少但最硬。对复杂逻辑抽象做单测或契约测试，验证边界条件。对组件层少做 snapshot，多做行为断言，减少噪音。

迁移期间评审的关注点也要变。别只看语法是否正确，要看行为合同是否更清晰、更容易被验证。

## 常见误区与反模式，把迁移做成组织性回归

这块我写得直接一些，因为我见过的很多团队的失败不是技术原因，而是反模式叠加。

### 反模式 1，Big Bang 一次性全量替换

一次性全量替换的诱惑来自「短痛」。看似只要熬过一段时间就结束了。

但实际工程里 Big Bang 会制造三类灾难。变量太多，回归无法定位。队伍被分裂成「迁移派」和「业务派」，沟通成本爆炸。迁移周期一旦拉长，组织耐心耗尽，最后只能降目标，「能跑就行」。

除非你的应用极小、依赖极少、上线风险极低，否则 Big Bang 几乎一定是错误策略。

### 反模式 2，把 Options API 机械翻译成 Composition API

机械翻译让你感觉进度很快。data 变 ref/reactive，computed 变 computed，methods 变 function。

但它会留下更大的技术债。你失去了 Options API 的组织结构，又没有建立新的抽象边界，最终组件会变成一个更难维护的脚本文件。

正确做法是，把复杂逻辑抽成 composable，把 UI 细节留在组件，把共享状态交给 store 或服务层。别把所有东西都塞进 setup()。

### 反模式 3，继续依赖全局副作用

event bus、隐式注入、模板 filter 这些东西，Vue 3 并不会自动消灭它们，甚至会让它们更难追踪，因为逻辑更分散了。迁移中如果不主动收敛全局副作用，你只是把旧问题搬到了新框架里。

### 反模式 4，把迁移当作「升级工具链」的借口

框架升级期间换构建工具、换 lint、换格式化、换目录结构，容易把团队拖进无意义的消耗。工具链升级当然有价值，但它必须服务于迁移目标，而且要分阶段做，别把风险叠加在同一个发布窗口。

## 一条可执行的分阶段路线，先搭桥，再分流，最后拆桥

我自己推荐的迁移路线可以概括为三句话。先搭桥，再分流，最后拆桥。

### 阶段 0，盘点与冻结「隐式接口」

在动代码之前，先盘点以下隐式接口。

全局注入，prototype 上挂了什么，http、logger、auth、feature flags。全局约定，filter、mixin、directive、全局组件。跨模块耦合，event bus、直接访问 store 模块内部结构、直接依赖路由实现细节。

这一步的产物不是文档，而是「迁移清单 + 风险列表」。你要知道哪些东西一动就会炸，哪些可以最后再动。

### 阶段 1，先把「平台能力」迁移到可替换的壳

平台能力包括路由壳、状态壳、网络壳、权限壳、错误边界、埋点等。把这些东西抽到明确的入口处，让组件不再靠隐式全局访问。你不需要一次性消灭所有全局访问，但要让新代码不再新增隐式依赖。

### 阶段 2，按业务域分批迁移，建立可重复的迁移模板

不要按页面迁移，而要按业务域迁移。一个域内的组件共享状态、共享交互、共享依赖，迁移时可以一起验证。

每迁移一个域，就总结模板。组件层怎么组织，哪些用 Options 哪些用 Composition。共享逻辑怎么抽，composable 还是 store。依赖怎么注入，参数、provide/inject 还是 globalProperties。回归怎么验证，e2e 覆盖哪些链路。

当模板稳定后，迁移速度会明显提升，且回归风险可控。

### 阶段 3，拆桥与清债

最后一阶段才是「清理」。移除兼容层、替换遗留全局副作用、统一抽象方式、补齐类型与测试。

很多团队失败在这里。他们在迁移中期就开始大规模清理，导致迁移速度下降，组织耐心耗尽。正确做法是先把业务迁过去，让新能力可用，然后再集中清债。

## 迁移成功与否，取决于你是否愿意把「隐式协作」变成「显式契约」

我对 Vue 2 到 Vue 3 迁移的最终判断很直接。

不要把迁移当作语法升级。真正要升级的是边界、依赖表达与回归机制。

不要追求全量改造的纯粹性。增量迁移不是妥协，而是风险控制手段。只要你的新代码不再制造旧债，增量是可收敛的。

迁移的核心胜利不是「组件都写 setup 了」，而是系统的隐式接口减少了，行为合同更清晰了，排障与迭代成本下降了。

如果你把迁移当作一次「把隐式协作改成显式契约」的工程重构，你会在 Vue 3 里获得长期收益。如果你只把它当作换一套写法，你会得到一个更现代但同样混乱的代码库，而且它更难救。

因为你以为自己已经升级过了。

那你的团队现在在哪个阶段？是还在纠结语法细节，还是已经开始建边界了？
