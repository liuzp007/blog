事情是这样的。

我之前接手过一个 Vue 2 的老项目，页面里有个表单，动态添加字段的那种。产品说加个「高级选项」，点击之后多出来几个输入框。我当时心想这很简单啊，就往对象上 `this.form.newField = ''` 一挂，完事。

结果页面上啥也没变。

我盯着屏幕愣了好几秒，数据明明有了，UI 就是不动。后来翻了翻文档才知道，哦，得用 `Vue.set`。坦率的讲，那一刻我有点不爽，觉得这框架怎么这么坑。

但后来冷静下来仔细想想，这事其实不怪框架。它不是坑，它是一个设计取舍，而且是一个在当时非常合理的设计取舍。只是你得先搞懂它到底取舍了什么，才能在项目里用得稳。

我自己的感受是，Vue 2 的响应式系统可能是前端框架里被误解最多的部分之一。很多人觉得它是「魔法」，也有人觉得它是「坑」。说真的，两种看法都不对。它就是一套工程折中方案，有自己的能力边界，也有非常清晰的契约。你遵守契约，它就稳定得一批。你绕开契约，它也不拦你，但后果自负。

今天想聊聊这套系统的边界到底在哪，以及怎么在大型项目里跟它和平共处。

## 先聊清楚它到底是怎么工作的

很多人把 Vue 2 说成「监听数据变化」。这话听着没毛病，但会把你带进一个错误的心智模型里。

Vue 2 实际追踪的不是「谁变了」，而是「谁读了谁」。

依赖关系建立的时机不是写入，是读取。写入只负责通知。这两者的区别非常大，你理解了这个，后面所有的边界问题就都能解释了。

一个更接近事实的模型是这样的。每个响应式属性身上挂了一个 Dep，你可以把它理解成一个订阅中心。当组件渲染或者计算属性执行的时候，会创建一个 Watcher，并且把自己设成全局的 Dep.target。然后属性身上的 getter 一触发，就会把当前这个 watcher 订阅进来。等到 setter 触发的时候，就通知所有订阅者，兄弟们，值变了，该更新了。

下面这段伪码能解释 80% 的行为，不追求跟源码一致，只追求机制准确

```js
class Dep {
  constructor() {
    this.subs = new Set()
  }
  depend() {
    if (Dep.target) this.subs.add(Dep.target)
  }
  notify() {
    for (const w of this.subs) w.update()
  }
}
Dep.target = null

function defineReactive(obj, key, val) {
  const dep = new Dep()
  let childOb = observe(val) // 深层递归
  Object.defineProperty(obj, key, {
    get() {
      dep.depend()
      if (childOb) childOb.dep.depend() // 让数组/对象整体也可被依赖
      return val
    },
    set(next) {
      if (next === val) return
      val = next
      childOb = observe(next)
      dep.notify()
    }
  })
}
```

有个特别重要的细节你得知道。依赖关系是动态的，是按运行路径建立的。也就是说，你的模板里有 `v-if`，条件不同，依赖集合就不同。上一次渲染读了 A 字段，这次分支进了 B 字段，那 A 就不在依赖集合里了。

这是响应式「聪明」的来源。同时也是某些诡异 bug 的温床。

## 对象新增属性，为什么拦不住

回到我开头踩的那个坑。

Vue 2 用 `Object.defineProperty` 来改写属性的 getter/setter。关键就在这了，它只能改写「已经存在的属性」。你往对象上新增一个 key，这个 key 从来没被 defineReactive 包装过，身上没有 dep，没有 getter/setter，当然就没有依赖收集，也没有通知。

坦率的讲，这就是 defineProperty 这个 API 本身的能力上限。它只能拦截已知属性，对未知属性无能为力。

Vue 2 给了一个补丁方法，就是 `Vue.set(obj, key, val)`。它内部会对新 key 调用 defineReactive，然后触发对象身上那个「整体 dep」去通知所有订阅者。能用，好使。

但我一直觉得，如果在项目里到处都是 `Vue.set` 和 `this.$set`，那往往意味着一个更深层的问题，你的数据结构在不断漂移。字段不稳定，状态 shape 缺乏统一约束。短期看你是在修 bug，长期看你是在把系统变得不可推断。

我自己更倾向的方案是，提前把对象的 shape 定死。不要把对象当成自由扩展的字典，而是当成有 schema 的数据结构。初始化的时候把可能用到的字段都声明出来，哪怕初值是 null 或者 undefined

```js
data() {
  return {
    // 把 shape 固定下来，后续只做赋值，不做新增 key
    form: {
      name: '',
      age: null,
      address: '',
      // 未来字段也预留
      extra: null
    }
  }
}
```

这样做的好处是多方面的。运行时层面减少漏更风险，协作层面降低联调不确定性，代码阅读层面让数据结构更可推断。你想想看，接手项目的人看到这个 data，一眼就知道这个对象会长什么样，而不是在代码里翻来翻去找哪里偷偷加了字段。

关键的工程判断是，新增属性到底应不应该被允许存在？在大型项目里，我更倾向于把它当成一种「危险行为」，只在少数场景开放，并且用结构约束把它变得可控。

## 数组的那点事

数组的问题跟对象类似，但更隐蔽。

数组的索引是动态的、可扩展的。你想想看，Vue 2 不可能为每一个潜在索引提前调用 defineProperty，它根本不知道你的数组将来会有多长。

所以 Vue 2 换了一条路。它拦截了数组的变异方法，push、pop、shift、unshift、splice、sort、reverse，一共七个。这些方法执行之后，对数组身上的「整体 dep」做 notify。

于是就有了一个很多人踩过的坑。`arr.splice(i, 1, x)` 能触发更新，`arr[i] = x` 不一定。`arr.push(x)` 能触发更新，`arr.length = 0` 也不一定。

这个事常被误读成「Vue 2 的数组更新有 bug」。其实不是 bug，它就是一套约定。Vue 2 在数组上提供的是「约定型更新接口」，你用它认识的那几个方法，它就能保证可观察。你绕开它，它就不保证。这里面没有道德判断，只有接口契约。

工程上我建议把数组变更统一收口成少数方法。尤其在 store 或者模块状态里，可以定个团队规范

不允许 `arr[index] = ...`，统一用 splice。不允许直接写 length，清空用 `splice(0)`。

你甚至可以在 code review 里把这个当硬规则审查。这不是洁癖，是为了把不可见的响应式边界变成可见的 API 选择。

## 深层递归的代价

说到这，还有一个跟性能相关的话题得聊。

Vue 2 的 observe 默认是深度递归的，会把对象嵌套结构全部走一遍 defineReactive。所以呢，有几件事得知道

初始化成本跟对象规模成正比，尤其是大列表、深树形结构会带来明显卡顿。内存开销也不可忽视，每个响应式 key 都有自己的 dep、闭包、getter/setter。而且有些场景你其实根本不需要深度响应式，比如只展示一次的数据，或者后续只会整体替换的数据。

工程策略上，你需要回答一个更根本的问题，哪些数据必须是响应式的，哪些不必？

常见的做法有三种。对于大体量数据，用整体替换而不是深度变更，拿到数据后不要逐字段 patch，而是直接替换引用触发更新。对于只读数据，用 `Object.freeze` 表达不需要响应式，让 Vue 跳过递归。对于频繁更新的数值集合，考虑把它们移出响应式系统，用 canvas、虚拟列表或者手动渲染来承载高频更新。

你可以这样明确表达「我不需要深度响应式」

```js
data() {
  return {
    // 大型静态配置：冻结后可减少误写与观察成本
    schema: Object.freeze({
      fields: [/* ... */],
      rules: { /* ... */ }
    }),
    // 大列表：整体替换，少做深层 patch
    rows: []
  }
},
methods: {
  async load() {
    const rows = await fetchRows()
    this.rows = rows // 替换引用触发更新
  }
}
```

这类做法的核心不是优化性能，而是把响应式当成一种有限资源来使用。当你不再把所有东西都交给响应式系统，系统反而更稳定。

## 计算属性，优雅的陷阱

计算属性可能是 Vue 2 响应式体验里最优雅的部分了。写起来舒服，用起来自然。

但说真的，它也是大型项目里隐性耦合的温床。

原因在于，computed 的依赖来自读取路径。你在代码里看不到显式的依赖声明。computed 内部读了哪些字段，这些字段一变，computed 就会失效，然后可能连锁触发渲染。

比较常见的坏味道是这样的，computed 里面做了过多的业务聚合，把好几个模块的状态揉成一个巨大的派生对象。结果就是任何一个小变更都引发大范围失效。或者 computed 内部读到了本不该读的响应式字段，比如某个只用于日志的状态，结果造成依赖污染，莫名其妙的重渲染就来了。

我的建议是，computed 只做结构稳定的派生，不做条件分支极多的业务决策。把复杂决策拆成多个小 computed，让依赖更局部。避免 computed 返回全新对象导致的引用抖动，尤其是作为子组件 props 的时候，必要时做结构共享或者把返回值拆成原子字段。

在 Vue 2 那个年代没有自动的依赖可视化工具，这些「依赖污染」往往是性能问题的根源之一。你盯着页面卡，翻了半天代码才发现某个 computed 里多读了一个字段，那种感觉真的是一言难尽。

## 几个常见的认知误区

聊聊我在项目中反复见到的几个误区。

第一个，以为数据变了 UI 就会变。坦率的讲，Vue 2 的响应式只对它能拦截到的写入负责。你用 `obj.newKey = 1`，你用 `arr[i] = x`，写入确实发生了，但 UI 不一定会更新。这事不是框架 bug，是你绕开了契约。

第二个，把任意对象塞进 data，然后在各处随意改。当一个对象同时被 Vue 响应式系统和外部逻辑共同持有，并且外部逻辑会直接改它的属性，你很容易出现写入路径不统一的问题。有时通过 setter，有时绕开 setter。最终的表现就是，同样的业务动作，有时更新有时不更新。真的很难排查。

解决思路不是多写 Vue.set，而是把写入路径收敛。定义状态的唯一写入口，store 或者 action 或者模块函数，外部逻辑只能通过这个入口请求变更。

第三个，把性能问题归咎于「响应式慢」。说真的，多数性能问题来自依赖范围太大和变更频率太高，而不是响应式本身。Vue 2 的响应式是足够快的，但它不是为 60fps 高频流数据设计的。你需要为高频场景选择不同的承载方式。

## 回到最初那个问题

回到我接手那个老项目的时候。

那个 `this.form.newField = ''` 的 bug，后来我用 Vue.set 修好了。但再后来我做了一次重构，把表单的 data 结构提前声明完整了，从那以后那个模块再也没有出现过类似的响应式丢失问题。

我自己的感受是，Vue 2 的响应式系统设计得其实挺好的。它用 `Object.defineProperty` 加依赖收集，在开发心智成本、运行时成本、实现复杂度和生态兼容性之间找到了一个长期稳定的平衡点。你觉得它好用，是因为它把依赖关系构建成了默认行为，不需要手动声明。你觉得它偶尔失手，是因为这套机制天然依赖能拦截到读取和写入，而有些操作它确实拦截不到。

但这个「拦截不到」不是什么致命缺陷。它就是一个边界，一个你可以预测、可以控制的边界。

关键在于，你愿不愿意把边界变成规则。数据结构尽量定型，数组更新收敛到约定接口，大体量数据敢于放弃深度响应式，computed 保持克制。做到这些，你会发现 Vue 2 的响应式其实一直很靠谱，它只是要求你像对待任何一个有边界的系统一样，尊重契约，控制出口，减少偶然性。
