## 先定目标，大型项目里稳定指的是可预测、可回滚、可定位

去年有个朋友找我喝茶，说他负责的那个 Vue 2 项目「稳得很」，快两年没动过框架版本了。我当时没接话，因为我知道他那个项目线上经常半夜报警，每次出问题全组人爬起来翻日志，一个 bug 定位大半天。坦率的讲，这不叫稳定，这叫运气还没用完。

很多人把「稳定」理解成「少改动」，这个想法挺自然的，但放在大型项目里不太对。需求还在变，依赖还在变，浏览器和安全合规要求也在变，你不改只是在把风险往后堆，堆到某一天突然爆掉。

我自己对稳定的定义比较朴素，就三个东西。能预测，同样的输入和环境，系统行为能复现，变更影响面能推断。能回滚，出了问题分钟级恢复，不用靠某个「神秘大佬」手工操作。能定位，线上问题能快速归因到具体模块、提交、配置，而且定位成本随系统规模增长得尽量慢。

Vue 2 本身不是稳定性的来源。稳定性的来源是围绕 Vue 2 建起来的工程体系。把这句话记住，你就不会老陷在「升不升级」的争论里，而是会把注意力放在真正能让系统稳的抓手上。

## 版本冻结的幻觉，不升级不等于风险归零

说真的，很多团队选择长时间维护 Vue 2 之后，心理上会自动把它等同于「稳定」。框架不变，行为不变，感觉风险就小了。

但实际情况完全反着来。你冻结了核心依赖，风险并不会消失，它会悄悄转移到别的地方累积起来。

浏览器环境一直在变，新特性、兼容性策略、性能特征都在变。你依赖的生态也在变，构建工具更新了，周边库升级了，安全漏洞被披露了。更不用说业务本身在变，状态数量在涨，页面数量在涨，协作人数也在涨。还有安全合规方面的压力，依赖漏洞、许可证变更、隐私法规，这些东西可不会因为你冻结了框架版本就原地踏步。

所以我一直觉得，「维护 Vue 2」真正要做的事情不是守着一个版本一动不动，而是构建一种能力，一种在不频繁大迁移的前提下持续吸收变化的能力。

## 稳定性的第一个抓手，把依赖关系做成可审计的图

大型 Vue 2 项目最常见的失控点不是模板写得多烂，而是依赖关系乱成一团。组件依赖组件，模块依赖模块，页面依赖工具库，工具库依赖全局状态。依赖不可见就不可治理，这话怎么强调都不过分。

工程上我自己习惯把依赖治理分成三层来看。

模块边界，用目录结构和导入规则约束哪些模块能依赖哪些模块。运行时边界，禁止跨层写入，比如业务组件直接写全局单例或者随意读写 localStorage 这种事。构建边界，约束打包输出和 chunk 结构，避免引入不可控的体积和加载链路。

一个马上就能落地的做法，给 src 目录下的模块制定导入白名单，配合 ESLint 规则或者简单脚本做校验。哪怕你不想搞复杂工具，也可以先从「禁止跨层相对路径」和「禁止从页面直接导入底层实现文件」这两条开始，慢慢收。

先跑起来再说，不用追求一步到位。

## 稳定性的第二个抓手，状态治理比组件治理关键得多

Vue 2 的组件体系本身维护起来并不难，真正难的是状态在系统里乱流。大型项目里状态失控通常长这样，同一个概念在好几个地方各存了一份，互相「同步」着。谁都能改，改完靠 watcher 修补一致性。一个字段最初代表 A，后来被复用成 A 加 B，最后谁也不敢删。

在 Vue 2 项目里，最有效的治理手段往往不是「重构组件」，而是建立状态层协议。

明确哪些状态属于组件内部、页面级、领域级共享。领域级共享状态必须通过 action 或 mutation 的意图入口修改，禁止随意写。对关键状态的变更建立日志和回放能力，至少在开发和预发环境要有。

举个例子，把写入口集中到 action，组件只表达意图。

```js
// 组件里
methods: {
  onSubmit() {
    this.$store.dispatch('order/submitOrder', { cartId: this.cartId })
  }
}

// store/modules/order.js
export const actions = {
  async submitOrder({ commit }, { cartId }) {
    commit('SUBMIT_START', { cartId })
    try {
      const res = await api.submit(cartId)
      commit('SUBMIT_SUCCESS', { orderId: res.id })
    } catch (e) {
      commit('SUBMIT_FAIL', { message: String(e) })
      throw e
    }
  }
}
```

你想想看，这段代码的工程价值在哪里。在于你能在一个地方看到状态怎么变化、失败怎么处理、回滚怎么实现。稳定性来自变更可追踪，不是来自不要改。

## 稳定性的第三个抓手，发布与回滚必须成为默认动作

大型项目里最让人害怕的场景是什么。线上出问题了，只能紧急修复然后祈祷。

真正稳定的系统需要把回滚做成默认能力，不是出了事才临时想的。

这其实不是 Vue 2 特有的问题，但 Vue 2 项目有自己的挑战。历史包袱导致构建输出不稳定，环境变量一大堆，灰度策略缺失，回滚变得特别贵。

一套能落地的发布和回滚策略可以从这几件事开始。

产物可复用，同一个 commit 在不同环境产物尽量一致，环境差异通过配置注入而不是代码分支。灰度和开关，关键功能用 feature flag 包装，允许逐步放量和快速关闭。版本可追踪，页面能显示当前版本号或 commit hash，日志里能关联到版本。回滚可自动，回滚不依赖重新打包，而是切换到上一份已经存在的产物。

你不必一次全做，但必须开始做。否则「稳定」这两个字就只能是贴在墙上的口号。

## 性能治理，Vue 2 项目稳定性的隐藏支柱

性能问题在大型项目里迟早会变成稳定性问题。卡顿导致误操作，超时导致重复提交，白屏导致用户流失。很多人优化 Vue 2 性能的套路就是加 computed、加 keep-alive，但很快就会撞墙，因为性能问题往往不是某个点的问题，是系统性的。

依赖范围过大，某个状态变更触发了大量组件更新。列表渲染过重，大列表加复杂行组件导致渲染成本飙升。资源加载失控，首屏 chunk 太大，异步 chunk 又太碎导致瀑布。

治理性能的关键是预算化，把性能从出了问题再救火变成持续约束。能落地的预算包括首页 JS 体积上限、首屏渲染时间目标、关键交互响应时间上限、长列表渲染策略。

在 Vue 2 中有一个经常被忽略但特别有效的动作，把高频更新的部分从响应式系统里移出去。比如用 canvas 或 requestAnimationFrame 手动更新，让 Vue 只负责低频结构更新。

稳定性来自系统承载能力匹配，不是来自优化某个函数。

## 可观测性，没有可观测就没有可维护

大型项目维护 Vue 2，有一种 bug 最让人崩溃。用户说卡了、白了、错了，但你在本地完全复现不了。

这种时候靠的不是英雄主义，是工程纪律。

最低限度的可观测性应该包括这几个东西。错误边界和全局异常捕获，能收集未处理异常、资源加载失败、Promise rejection。关键链路埋点，至少记录页面加载成功或失败、关键 API 成功或失败。性能指标采样，首屏、路由切换、长任务这些。

Vue 2 自己的错误边界能力确实有限，不像 React 那样有完整方案，但你仍然可以通过全局 errorHandler、window.onerror、unhandledrejection 做基本兜底，然后把信息关联到版本号和路由。

这块说到底就是一句话，你得能看见问题，才能谈解决。

## 故障演练，稳定性靠演过一次而不是靠相信不会发生

很多团队把稳定性建设理解成加监控加告警。这些东西确实重要，但如果你从来没做过故障演练，真正出问题的时候你会发现，你知道发生了什么，但你不知道该怎么恢复。

我自己的感受是，应该把演练当成一个产品能力去建设，至少覆盖三类场景。

资源加载失败，比如 CDN 局部不可用、某个 chunk 404、缓存命中旧版本导致运行时报错。API 异常，关键接口超时、返回结构变化、幂等性失效导致重复提交。版本回滚，新版本引入严重 bug，需要在分钟级切回上一版本。

每一类演练都应该产出一个最小恢复路径。谁负责判断，切哪个开关，怎么验证恢复成功，如何防止二次扩散。

演练的价值不是证明你有多强，而是把恢复路径从人的脑子里搬到流程和脚本里。

下面给一个非常务实的做法，构建时注入版本号，页面底部或 debug 面板能看到，同时在日志上报中带上版本号和路由，定位才有锚点。

```js
// build-time: 注入版本号（示意）
window.__APP_VERSION__ = '2026-03-24-<commit>'

// runtime: 错误上报携带版本与路由
window.addEventListener('unhandledrejection', e => {
  reportError({
    type: 'unhandledrejection',
    message: String(e.reason || ''),
    version: window.__APP_VERSION__,
    route: location.pathname + location.search + location.hash
  })
})
```

注意，这里的重点不是上报到哪里，而是你要在系统里形成一条可追踪链路。用户看到的问题能关联到日志里的版本，版本能映射到 commit，回滚能切回旧产物。这条链路通了，定位问题才有抓手。

## 依赖收敛的落地细则，把可以依赖变成工具能检查的规则

很多人认同要有边界，但边界经常停留在 PPT 里。大型项目要把边界落地，需要两个条件。

规则足够简单，团队能执行。规则可被工具检查，否则会被忙碌吞没。

一个从零开始也能落地的方案是这样的。把 src 目录按层级拆分，比如 pages、features、components、utils、store，然后定义禁止逆向依赖的硬规则。

utils 不能依赖 components、features、pages。components 不能依赖 pages。features 可以依赖 components、utils、store，但不能依赖 pages。

你不需要一开始就做复杂的架构图，先把最危险的逆向依赖堵住就行。然后用 ESLint 或简单脚本做检查，把违规变成 CI 失败，而不是代码评审里的「建议」。

哪怕只是伪码式的检查脚本，也能立刻提升稳定性，因为它让依赖扩散变难了。

```js
// 伪码：扫描 import 路径，发现逆向依赖就报错
if (from.startsWith('src/utils/') && to.startsWith('src/pages/')) fail()
if (from.startsWith('src/components/') && to.startsWith('src/pages/')) fail()
```

稳定性建设经常被低估的一点就是，把规则工具化之后，团队的注意力才能从反复提醒转移到解决真正问题上。

## 常见误区，把维护工作等同于修 bug

修得快不等于稳。

真正稳的系统会让 bug 变少、变浅、变容易定位。你需要把一部分精力投入到让 bug 不再出现的机制上，比如写入口收敛、回滚能力、依赖边界。

还有一个误区是只优化组件不治理状态与依赖。你可以把某个组件重构得很漂亮，但如果它依赖的状态仍然全局可写，依赖链仍然不可见，系统照样会在别的地方崩。维护的优先级应当从结构性风险开始，而不是从局部优雅开始。

再说一个常见的想法，把升级当作唯一解决方案。升级到 Vue 3 能带来很多收益没错，但如果你没有治理能力，升级只会把问题搬家。耦合仍然耦合，发布仍然不可回滚，性能仍然不可预算。升级是手段，不是稳定性的来源。

## 反模式，用全局技巧掩盖结构问题

大型 Vue 2 项目里有一个特别常见的反模式，系统出现不一致或者性能问题的时候，靠全局技巧修补，而不改变结构。

到处加 watcher 维持状态一致性，最后形成更新链地狱。到处加 nextTick 试图修复时序，最后把渲染调度变成偶然。到处用 event bus 解决跨层通信，最后依赖关系不可审计。把所有东西塞进 Vuex，最后全局状态成了耦合垃圾场。

这些技巧在局部问题上可能真的有效，我不否认。但在系统层面会持续放大维护成本。你需要用边界治理替代全局技巧。

这不是一朝一夕的事，但方向得对。

## 我的判断，维护 Vue 2 的关键是建立演进能力

我支持长期维护 Vue 2，但前提是你把目标从「尽量不动」改成「可持续演进」。

我自己判断一个 Vue 2 项目维护得好不好的标准就这几条。依赖关系可审计，模块边界能被工具或规范约束。状态写入口收敛，关键状态变更可追踪。发布与回滚是默认动作，线上事故不靠英雄主义。性能有预算，资源加载与更新范围可控。具备基本可观测性，定位成本可接受。

当这些能力成立的时候，你维护的是一个可治理的系统，Vue 2 只是其中一个实现细节。当这些能力不成立的时候，就算你升级到再先进的框架，系统仍然不会稳定。

稳定性从来不是来自不升级。

是来自工程体系。

你们团队现在维护 Vue 2 项目的时候，最头疼的是什么。
